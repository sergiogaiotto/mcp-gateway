# Como contribuir com o RaPA

## Regras do projeto

- **Só código aberto.** Toda dependência precisa de licença aprovada pela OSI. Bibliotecas com GPL ou AGPL não podem ser importadas no processo do RaPA; só rodam como serviço separado e sem modificação.
- **Sem LLM nas execuções.** O executor só interpreta a lista de passos. O modelo de linguagem entra apenas para criar e consertar robôs, e sempre como proponente: o código decide.
- **A empresa é fronteira obrigatória.** Toda tabela com dados de empresa tem `company_id` e isolamento por linha; nada que venha de um usuário escolhe a empresa, que sempre vem do token.
- **Segredos nunca aparecem** em eventos, logs, prompts, telas ou resultados. O executor digita o valor do cofre na hora; o resto do sistema só vê a referência.
- **Nada que gravou é repetido automaticamente.** O executor só começa um passo que grava depois que o plano de controle registra o aviso; a partir daí a execução nunca volta para a fila: se parar, falha (e uma pessoa confere o sistema de destino). Depois de um passo irreversível, uma falha vira estado "indeterminado" e uma pessoa decide.

## Organização do código

```
src/rapa/
  core/       formato do robô, templates, política, edições, contratos e eventos
  runner/     executor sobre Playwright
  recorder/   gravador da demonstração
  compiler/   compilação da gravação em robô
  llm/        cliente do hub de LLM, sonda e generalização
  control/    plano de controle: banco, fila, API REST e gateway MCP
  ui/         interface em NiceGUI
  fixtures/   portais de teste e robôs de exemplo
  server.py   montagem do serviço num processo só
tests/e2e/    o serviço inteiro sobre PostgreSQL, Chromium e o portal de teste
```

Os módulos conversam pelos contratos de `rapa.core.contracts` e `rapa.core.events`. Mudanças no formato do robô (`rapa.core.robot`) exigem subir `schema_version` e escrever a migração.

## Regras do gravador e do compilador

As regras completas estão nas docstrings de `rapa.recorder.sensitivity`, `rapa.recorder.recorder` e `rapa.compiler.lowering`, e no cabeçalho de `capture.js`. Na dúvida, o passo grava e o valor fica fora da gravação. Em resumo:

- **Login só com credenciais.** O envio só é autenticação quando a página só teve credenciais de uma credencial: o usuário com uma senha `type=password` de verdade (e, se houver, o código de uso único); usuário e código sem senha nunca é login. Só códigos só é login com o botão num `<form>` cujos campos de texto são só códigos, os mesmos que foram preenchidos; sem esse `<form>`, nunca, qualquer que seja o texto do botão.
- **Resíduo conhecido.** Um `<form>` só com o código continua login mesmo que a página use o código para confirmar uma operação. Como só os campos de texto contam, isso inclui o `<form>` do código com o valor num `<input type=hidden>` ou com uma lista que a pessoa não mexeu; dois `<form>` iguais só com o código na mesma página não se distinguem.
- **Shadow roots.** Um campo de shadow root aberto nunca é credencial de login e, numa página com senha ou código, o valor dele sai da gravação e o campo vira uma entrada do robô; só o `type=password` de um componente continua a senha do cofre, no campo dele. Ele é identificado pelo caminho dos hospedeiros e localizado por um seletor que atravessa os shadow roots abertos (`#hospedeiro > #campo`), além do papel, do rótulo, do placeholder e do `data-testid`, contados no documento e em todos os shadow roots abertos.
- **Quando sai o valor de um campo de texto de shadow root.** No `change` do próprio shadow root (o gravador põe ouvintes de `change`, `blur` e `focusout`, na fase de captura, em cada shadow root aberto que aparece no caminho de um evento), antes do blur e na ordem da pessoa, ou no `focusout`. Se o componente para o `change`, o valor sai antes da próxima ação noutro elemento (`pointerdown`, `keydown` ou `beforeinput`) ou no `blur`, que o gravador ouve na fase de captura da janela e do shadow root (também quando a pessoa sai para um iframe). Nesses quatro eventos o gravador só tira um retrato do campo (o descritor e o valor) e decide num `setTimeout`, depois dos ouvintes de blur do componente: o campo ainda na página sai com o descritor de agora (o que virou `type=password` ou código só sai como segredo); o que saiu da página sai com o retrato. Um clique e as teclas Enter, Tab e Esc mandam os valores pendentes na hora, antes de a ação ser gravada. Se o componente já tirou o campo da página quando o `change`, o `blur` ou o `focusout` chega (ou quando a janela perde o foco, só para campos de shadow root), o passo fica com o retrato que o gravador tirou depois da última tecla da pessoa (num `setTimeout`, com a tecla já aplicada e o campo ainda na página), mas o valor desse retrato só sai como segredo: a página pode ter mudado o campo depois dele (uma máscara que só aparece depois, uma tecla que ela aplica num temporizador), então o robô nunca o repete e pede o valor numa entrada (ou usa a credencial do cofre, se o retrato diz que o campo é senha, código ou usuário). Só o retrato que o gravador tirou ao guardar o campo (na próxima ação ou no blur, com o campo ainda na página, sem tecla nem valor de script depois) vale como o valor. Na tecla (`beforeinput` ou `input`), o valor guardado fica desconhecido até o retrato seguinte.
- **Marcas de sigilo só sobem.** Senha (inclusive a máscara por CSS), código de uso único, papel de login (o usuário ou outro campo de um login) e nome (também o atributo `name` ou o id) que fala em senha, em assinatura eletrônica ou digital ou em código de transação ou de segurança (a senha de transação: o valor nunca sai, e o robô o pede numa entrada, nunca a senha do cofre): cada retrato do campo (depois de cada tecla, no `blur` e antes da próxima ação; nunca só no foco, para que o mesmo input que a página reaproveita de "Senha" para "Valor (R$)" não leve a marca de senha) soma as marcas dos anteriores até o valor sair, e o envio leva todas. O campo que era senha, código ou de um login quando a pessoa o focou só sai como segredo e vira uma entrada do robô, sem virar outra credencial do cofre: a senha que a pessoa mostra com o "olho" antes de digitar nunca sai como texto, e o campo que a página reaproveita de "Senha" para "Valor (R$)" pede o valor numa entrada; o campo que saiu da página soma ainda as do próprio elemento e a de qualquer senha ou código no documento. Um valor sigiloso só sai como segredo, para a limpeza. Depois do envio, a próxima edição do campo começa outro retrato.
- **Nada de shadow DOM é embrulhado.** `attachShadow`, `addEventListener`, `composedPath`, `focus` e `blur` continuam nativos. O único nativo que o gravador troca é a propriedade `value` de `HTMLInputElement` e `HTMLTextAreaElement` (`hookValueSetter`, o getter e o setter): o getter só repassa, e o setter só marca o valor que a página muda enquanto a pessoa digita.
- **Resíduos dos shadow roots.** Shadow roots fechados ficam invisíveis. Um componente que só vira senha depois da decisão do gravador (no `focusout`, num temporizador ou num quadro do blur), com um nome que não fala em senha nem em assinatura, ainda sai como texto. Um componente que formata o valor no blur ("1234" vira "1.234,00") grava o valor formatado; o robô o digita tecla a tecla e a página o formata de novo, e então a conferência do texto digitado falha o passo, sem gravar. Um código em seis caixas de um caractere vira seis passos com o código inteiro, e o site o recusa (falha fechada). O campo que sai da página antes do retrato de depois da última tecla da pessoa (o componente o troca no próprio `input`, por exemplo) é esquecido, e também o que sai sem nenhum `change`, `blur` ou `focusout` que o gravador veja e sem a janela perder o foco (o componente para o `change` e o foco muda por script no mesmo documento); um campo da luz que some no próprio blur quando a pessoa sai para um iframe também. Então o robô fica sem o passo (falha fechada), nunca com um valor guardado antes da última tecla (uma tecla que a página só aplica depois, num temporizador dela, não é vista). O valor que sai antes do blur vai com o descritor desse momento: o campo que só vira senha no próprio blur ainda sai como texto quando o valor sai no `change` (que o navegador dispara antes do blur, quando o componente não o para) ou numa tecla Enter, Tab ou Esc no próprio campo.
- **Resíduos abertos do gravador (achados na verificação da rodada 11, também nas versões anteriores).** A senha ainda sai como texto quando a pessoa a mostra com o "olho" antes de pôr o foco no campo, quando a página a mostra no próprio `focus` do campo (antes do ouvinte de `focusin` do gravador) e quando o "olho" troca o `<input>` de senha por outro, de texto. Com o foco automático na senha, a senha mostrada e digitada e o usuário digitado depois, o usuário sai como texto. "Código de segurança do pedido" e um campo com `name="codigo"` contam como código de uso único, e o robô digitaria o código do cofre no lugar do que a pessoa digitou; um campo com `autocomplete=username` é ligado ao usuário do cofre mesmo sem um login confirmado. Um componente que troca o rótulo no próprio blur sai como texto. Perda de disponibilidade: um filtro chamado "Código de transação" vira uma entrada, e a chave da linha com o mesmo valor sai da gravação; o passo nessa linha falha sem agir.
- **Um passo, um elemento.** Edições, marcações e escolhas só se juntam num passo quando são do mesmo campo (a mesma descrição, inclusive o `data-testid`) e do mesmo elemento (o número que o gravador dá a cada elemento): o alvo e o valor de um passo sempre vêm do mesmo elemento.
- **Clique duplo.** O segundo clique (`detail` 2 ou mais, o mesmo seletor) some no passo do primeiro no mesmo elemento e também noutro elemento sem prova de outro alvo (outra chave da linha, outro texto, outro nome, outro rótulo ou outro `data-testid`): o número do elemento sozinho não separa os cliques. Com essa prova, ele só é outro passo quando cada um dos dois cliques gravou algo e o segundo gravou noutro endereço (ou com outro método) que o primeiro: a mesma gravação de novo é o clique duplo num botão que o primeiro clique mudou ("Pagar" que vira "Pagando…", a linha que vira "Processando"), e o robô age uma vez. Resíduos, em que o robô age menos que a pessoa, nunca mais: o clique duplo num botão sem trava que a página recria entre os cliques (cada clique grava) fica um passo só, e o botão de outra linha que sobe para o lugar do que a pessoa clicou, com o mesmo seletor cortado e nada mais diferente ou gravando no mesmo endereço (a linha só no corpo ou na consulta da requisição), também (o robô exclui um onde a pessoa excluiu dois).
- **Limpeza sem caixa.** Os valores sigilosos saem de todo texto que pode chegar ao robô ou ao modelo de linguagem, em maiúsculas ou minúsculas; só os valores digitados, a chave da linha e os endereços são trocados pelo valor exato.

## Regras do executor

As regras completas estão na docstring de `rapa.runner.interpreter`. Na dúvida, o passo grava e falha fechado antes de agir. Em resumo:

- **Rede contra ações repetidas.** Uma ação que grava numa linha (a página e o texto que a escolhe) conta em cada endereço por onde a página principal passa depois dela, até o fim da volta e, depois, até o fim da repetição, menos os que o próprio `navigate` do robô abre. Perdas de disponibilidade conhecidas, que falham fechado: escolher a página por um clique (um link) numa volta seguinte, e uma página aberta por um `navigate` que vai sozinha a outro endereço depois (`replaceState`, `meta refresh`, redirecionamento por script).
- **Confirmação.** A espera pela confirmação do anúncio de um passo que grava tem só o prazo da própria confirmação, nem o do passo nem o da execução: o lançador mata o processo do executor 15 s depois do prazo da execução, e o passo nunca age se esse prazo acabou durante a espera. Depois da confirmação do aviso de passo irreversível, o alvo, a linha única e a rede são conferidos de novo, na mesma página da primeira conferência; se a página for outra, o passo falha sem agir. Perda de disponibilidade aceita: uma página que sai e volta ao mesmo endereço durante essa espera também é recusada, porque a volta conta como da ação anterior na mesma linha.
- **Agir no elemento conferido, na hora de agir.** Um passo que grava age no elemento que foi conferido, nunca no que o localizador encontrar depois em outro documento. A espera pelo elemento (visível, habilitado e parado; editável para digitar; a opção na lista) vem antes, sem mandar nenhuma entrada à página. Depois dela, o contador de navegações da página principal (de outro documento e do mesmo documento: `pushState`, `replaceState`, `#`), a página e, numa linha escolhida pelo texto, a linha única com o elemento dentro dela são conferidos de novo. A ação vai sem `force`: o Playwright ainda confere que o alvo não está coberto, também por outro documento (um iframe por cima do botão, a página por cima de um iframe), nem inerte (um diálogo modal), e espera ficar livre. Um vigia na fase de captura da janela confere o primeiro evento da ação: se ele não cai no alvo, se o endereço mudou ou se a linha não tem mais um elemento cujo texto inteiro é a chave (a linha reaproveitada de "12" para "120" não vale), a ação inteira é cancelada; um clique cujos eventos não chegam à janela do alvo também falha. Em qualquer desses casos o passo falha sem agir (`elemento_ambiguo`). Num clique, numa marcação ou numa escolha, o vigia também confere que os campos digitados do mesmo documento ainda têm o valor que a releitura leu: a página que troca o logradouro enquanto o clique espera uma camada de "buscando CEP" sair faz o passo falhar sem agir (`acao_falhou`). O vigia só lê os campos do documento do alvo: com campos digitados noutro documento (o logradouro na página principal e o Salvar num iframe), o clique ou a marcação espera, só lendo a página e rolando o alvo para a janela como o Playwright, que o alvo fique livre no documento dele e nos documentos da mesma origem acima dele (uma camada com `pointer-events: none` ou `inert` conta como coberta), e só então os campos são relidos; se o alvo continua coberto quando falta menos de 1 s do prazo do passo, o passo falha sem agir (`tempo_do_passo_esgotado`). Um primeiro evento que chega mais de 0,5 s depois do vigia (o Playwright esperou algo que essa espera não vê, como uma página de outra origem por cima do iframe do alvo, ou uma camada que chegou logo depois dela) é recusado (`acao_falhou`). Marcar uma caixa que já está como deve ficar não manda evento nenhum e não é recusa. Um botão montado de novo na mesma linha durante a espera, sem navegação, leva a uma nova conferência completa, uma vez; na segunda vez, ou se a página trocou de documento durante a espera, o passo falha sem agir (`acao_falhou`). Perdas de disponibilidade aceitas: qualquer mudança de endereço da página principal entre a conferência e a ação (também um filtro que muda a consulta do endereço), uma tecla para um elemento que não recebe o foco, e uma linha cuja célula da chave ganha texto quando o mouse passa por cima (um ícone de editar).
- **Texto conferido.** Depois de digitar um texto, o valor do campo é conferido. Se a página mudou o campo, o texto é digitado de novo, e vale se o campo ficar com ele ou exatamente com o que ficou da primeira vez (a máscara da própria página); senão, o passo falha. Num passo que grava, nada é digitado de novo: vale o texto como o navegador o guarda (posto numa cópia solta do campo: `\r\n` vira `\n`, um e-mail perde os espaços das pontas), com os brancos (e o espaço rígido) normalizados, ou, num texto sem letras, a máscara da página: os mesmos dígitos na mesma ordem (CPF, CNPJ, CEP, telefone, data, centavos), com o sinal de menos, e, num número com casas decimais ou com o ponto dos milhares, o mesmo número ("1234,5" pode virar "R$ 1.234,50"; "10,5" que vira "1,05" e "1.234,00" que vira "123.400,00" não valem). Um campo vazio nunca vale por um texto, e num `input[type=number]` a regra dos dígitos não vale. O texto que só mudou de brancos também vale, e um inteiro pode ganhar casas decimais zeradas ("10" vira "10,00"); maiúsculas trocadas não valem. Qualquer outra diferença, como o `maxlength` que cortou o texto ou uma página que troca letras, faz o passo falhar. Os valores do campo nunca vão para eventos nem mensagens.
- **Campos digitados, lidos de novo antes de gravar.** Os campos de texto que o robô digitou são lidos de novo antes de cada passo que grava e age na página e comparados com a referência deles: o valor da digitação, ou o do fim do último clique, tecla ou escolha do robô. O que muda durante esses passos vale (a sugestão escolhida num autocompletar, a busca que a página limpa depois do Enter), mas só para os campos que ainda tinham a referência logo antes de o passo agir: o campo que a página já tinha mudado (durante uma espera) fica com a antiga. A formatação que a página põe quando o foco sai do campo vale pela comparação (brancos, máscara, "10" que vira "10,00", "10.00" ou "10,00 €"; nunca "10,00 mil", nem um número negativo que não foi digitado: o sinal de menos antes do primeiro dígito, também o U+2212 e o traço, os parênteses em volta e o sinal depois do último dígito); o que a página muda sozinha enquanto o robô espera ou digita noutro campo, também depois de um `pushState` ou `replaceState` (uma consulta de CEP que responde depois), faz o passo falhar sem agir (`acao_falhou`). Um campo digitado de novo vale pela última vez, e um que saiu da página (ou cujo documento acabou) deixa de contar; cada campo é lido no próprio documento, também num iframe. Fora da conferência antes de gravar, a leitura dos campos tem um prazo curto: numa página travada, nenhum ganha referência nova. Resíduos: a mudança que chega durante um clique, uma tecla ou uma escolha do robô vira a referência (também a que chega enquanto um passo que só lê, como abrir uma aba, espera uma camada sair), e a que chega entre a releitura e a ação de um passo de digitar ou de teclar (ou, num campo de outro documento, até 0,5 s depois da releitura) não é vista. A comparação aceita as máscaras de centavos, então "10" que vira "1,0" também vale, e um "D" de débito depois de um inteiro ("10 D") também. Perdas de disponibilidade aceitas: um campo digitado que a página reescreve quando o mouse chega ao botão, ou que ela monta de novo com o mesmo valor enquanto o clique espera, faz o passo falhar; um código com hífen antes dos números ("OS-12345") conta como negativo, e uma unidade com letras depois das casas zeradas ("10,00 kg") não vale.
- **Resíduos conhecidos.** A conferência da linha única não vê shadow roots fechados nem uma chave que só o CSS mostra, sem nada no HTML (o `content` de um `::before`); uma lista virtual que troca o que a linha é sem trocar o texto dela também não é vista. Um ouvinte da própria página na janela, posto antes do vigia, vê o evento antes dele, e a linha trocada entre o primeiro e o último evento de um clique não é vista (o vigia decide no primeiro). Um segredo vai para o elemento em que a origem foi conferida, sem o vigia.

## Antes de abrir um PR

```bash
uv run ruff format src tests
```

```bash
uv run ruff check src tests && uv run mypy
```

```bash
uv run pytest
```

Marcadores do pytest: `browser` (abre o Chromium), `database` (precisa de PostgreSQL) e `slow` (testes longos, como 100 reexecuções).

Textos para usuários, mensagens de erro e documentação ficam em pt-BR.
