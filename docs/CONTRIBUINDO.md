# Como contribuir com o RaPA

## Regras do projeto

- **Só código aberto.** Toda dependência precisa de licença aprovada pela OSI. Bibliotecas com GPL ou AGPL não podem ser importadas no processo do RaPA; só rodam como serviço separado e sem modificação.
- **Sem LLM nas execuções.** O executor só interpreta a lista de passos. O modelo de linguagem entra apenas para criar e consertar robôs, e sempre como proponente: o código decide.
- **A empresa é fronteira obrigatória.** Toda tabela com dados de empresa tem `company_id` e isolamento por linha; nada que venha de um usuário escolhe a empresa, que sempre vem do token.
- **Segredos nunca aparecem** em eventos, logs, prompts, telas ou resultados. O executor digita o valor do cofre na hora; o resto do sistema só vê a referência.
- **Nada que gravou é repetido automaticamente.** O executor só começa um passo que grava depois que o plano de controle registra o aviso; a partir daí a execução nunca volta para a fila: se parar, falha (e uma pessoa confere o sistema de destino). Depois de um passo irreversível, uma falha vira estado "indeterminado" e uma pessoa decide.

## Organização do código

```
src/rapa/
  core/       formato do robô, templates, política, edições, contratos e eventos
  runner/     executor sobre Playwright
  recorder/   gravador da demonstração
  session/    hospedeiro da sessão de gravação ao vivo (Chromium, gravador e canal)
  compiler/   compilação da gravação em robô
  repair/     candidatos do conserto a partir do retrato da página que quebrou
  llm/        cliente do hub de LLM, sonda, generalização e escolha do conserto
  control/    plano de controle: banco, fila, agendas, webhooks, lotes, credenciais e A1, evidências e retenção, API REST e gateway MCP
  ui/         interface em NiceGUI
  fixtures/   portais de teste e robôs de exemplo
  server.py   montagem do serviço num processo só
tests/e2e/    o serviço inteiro sobre PostgreSQL, Chromium e o portal de teste
```

Os módulos conversam pelos contratos de `rapa.core.contracts` e `rapa.core.events`. Mudanças no formato do robô (`rapa.core.robot`) exigem subir `schema_version` e escrever a migração.

## Regras do gravador e do compilador

As regras completas estão nas docstrings de `rapa.recorder.sensitivity`, `rapa.recorder.recorder` e `rapa.compiler.lowering`, e no cabeçalho de `capture.js`. Na dúvida, o passo grava e o valor fica fora da gravação. Em resumo:

- **Login só com credenciais.** O envio só é autenticação quando a página só teve credenciais de uma credencial: o usuário com uma senha `type=password` de verdade (e, se houver, o código de uso único); usuário e código sem senha nunca é login. Só códigos só é login com o botão num `<form>` cujos campos de texto são só códigos, os mesmos que foram preenchidos; sem esse `<form>`, nunca, qualquer que seja o texto do botão.
- **Credenciais do cofre só com certeza.** O usuário, também o que a página declara com `autocomplete=username`, só vira o usuário do cofre num login confirmado; fora dele (a página de recuperar o acesso, um envio "OK"), o valor, que não sai da gravação, vira uma entrada do robô. O código de uso único vira o código do cofre quando diz isso com clareza (`autocomplete=one-time-code`, um nome ou id como `otp`, `totp` ou `codigo_verificacao`, ou um rótulo que fala em código de verificação ou de autenticação, código SMS ou OTP ou dois fatores) e não é de uma operação. O campo que só é código por um sinal ambíguo ("Código de segurança do pedido", que também é o CVV ou o código de um pedido; "Token" sozinho, no rótulo, no nome ou no id, que também é o token de uma API; o nome ou o id `codigo` sozinho; "Código recebido por SMS"; o nome `otp_input`) continua sigiloso, mas só vira o código do cofre num login confirmado que tem senha ou que vem logo depois de um login confirmado com senha (a página do segundo fator): entre o envio do login com senha e o código, nenhuma outra ação da pessoa (só o Tab), nenhum endereço digitado e a mesma aba. O `<form>` só com o código e um botão de login, sozinho, depois de passar pelo menu, de digitar um endereço ou noutro site, pode ser o código de um pedido ou de um convite. O código de acesso ("Código de acesso", ou o nome ou o id `codigo_acesso`, sem um sinal claro de código de uso único), que em alguns portais é um código fixo que a pessoa guarda como uma senha (o CPF, o código de acesso e a senha do e-CAC), nunca vira o código do cofre, nem num login confirmado com senha; o de uma operação (o token da transação, o código de verificação do cartão), também nunca. Fora disso, o robô pede o valor numa entrada, com um aviso que diz por quê, nunca digita o código do cofre no lugar do que a pessoa digitou. A senha nova (`autocomplete=new-password`: "Nova senha", "Confirme a nova senha", "Crie uma senha") nunca é a senha do cofre (o robô digitaria a senha de agora onde a pessoa digitou outra): vira uma entrada, com aviso; a senha atual (`autocomplete=current-password`) continua a do cofre. O código num campo `type=password` ("Token", "Código de verificação") nunca é a senha do cofre: segue as regras do código; só o campo cujo rótulo (ou placeholder) fala em senha continua a senha, mesmo com `name="token"`.
- **Resíduo conhecido.** Um `<form>` só com o código continua login mesmo que a página use o código para confirmar uma operação. Como só os campos de texto contam, isso inclui o `<form>` do código com o valor num `<input type=hidden>` ou com uma lista que a pessoa não mexeu; dois `<form>` iguais só com o código na mesma página não se distinguem. O código ambíguo desse `<form>` só vira o código do cofre logo depois de um login confirmado com senha; sozinho ou depois de outra ação da pessoa, vira uma entrada.
- **Shadow roots.** Um campo de shadow root aberto nunca é credencial de login e, numa página com senha ou código, o valor dele sai da gravação e o campo vira uma entrada do robô; só o `type=password` de um componente continua a senha do cofre, no campo dele. Ele é identificado pelo caminho dos hospedeiros e localizado por um seletor que atravessa os shadow roots abertos (`#hospedeiro > #campo`), além do papel, do rótulo, do placeholder e do `data-testid`, contados no documento e em todos os shadow roots abertos.
- **Quando sai o valor de um campo de texto de shadow root.** No `change` do próprio shadow root (o gravador põe ouvintes de `change`, `blur` e `focusout`, na fase de captura, em cada shadow root aberto que aparece no caminho de um evento), antes do blur e na ordem da pessoa, ou no `focusout`. Se o componente para o `change`, o valor sai antes da próxima ação noutro elemento (`pointerdown`, `keydown` ou `beforeinput`) ou no `blur`, que o gravador ouve na fase de captura da janela e do shadow root (também quando a pessoa sai para um iframe). Nesses quatro eventos o gravador só tira um retrato do campo (o descritor e o valor) e decide num `setTimeout`, depois dos ouvintes de blur do componente: o campo ainda na página sai com o descritor de agora (o que virou `type=password` ou código só sai como segredo); o que saiu da página sai com o retrato. Um clique e as teclas Enter, Tab e Esc mandam os valores pendentes na hora, antes de a ação ser gravada. Se o componente já tirou o campo da página quando o `change`, o `blur` ou o `focusout` chega (ou quando a janela perde o foco, só para campos de shadow root), o passo fica com o retrato que o gravador tirou depois da última tecla da pessoa (num `setTimeout`, com a tecla já aplicada e o campo ainda na página), mas o valor desse retrato só sai como segredo: a página pode ter mudado o campo depois dele (uma máscara que só aparece depois, uma tecla que ela aplica num temporizador), então o robô nunca o repete e pede o valor numa entrada (ou usa a credencial do cofre, se o retrato diz que o campo é senha, código ou usuário). Só o retrato que o gravador tirou ao guardar o campo (na próxima ação ou no blur, com o campo ainda na página, sem tecla nem valor de script depois) vale como o valor. Na tecla (`beforeinput` ou `input`), o valor guardado fica desconhecido até o retrato seguinte.
- **Marcas de sigilo só sobem.** Senha (inclusive a máscara por CSS), código de uso único, papel de login (o usuário ou outro campo de um login) e nome (também o atributo `name` ou o id) que fala em senha, em assinatura eletrônica ou digital ou em código de transação ou de segurança (a senha de transação: o valor nunca sai, e o robô o pede numa entrada, nunca a senha do cofre): cada retrato do campo (depois de cada tecla, no `blur` e antes da próxima ação; nunca só no foco, para que o mesmo input que a página reaproveita de "Senha" para "Valor (R$)" não leve a marca de senha) soma as marcas dos anteriores até o valor sair, e o envio leva todas. O campo que era senha, código ou de um login quando a pessoa o focou só sai como segredo e vira uma entrada do robô, sem virar outra credencial do cofre: a senha que a pessoa mostra com o "olho" antes de digitar nunca sai como texto, e o campo que a página reaproveita de "Senha" para "Valor (R$)" pede o valor numa entrada; o campo que saiu da página soma ainda as do próprio elemento e a de qualquer senha ou código no documento. O rótulo que fala do código enviado ou recebido (por SMS, e-mail, celular ou WhatsApp) e o nome ou o id com `otp`, `totp`, `mfa` ou `2fa` como palavra (`otp_input`) também fazem do campo um código de uso único. O campo de texto sem rótulo que só o texto da página diz ser um código (o texto do `aria-describedby` dele ou, num campo com cara de código, com `inputmode=numeric`, `type=tel` ou `type=number` ou `maxlength` de 4 a 10, o texto logo antes dele ou de um dos três primeiros pais: "Digite o código que enviamos por SMS") só sai como segredo e vira uma entrada, sem a marca de código: nunca o código do cofre nem outra credencial, e não muda a forma de um login. O campo sem rótulo depois de "Digite o CEP" continua com o valor digitado. Um valor sigiloso só sai como segredo, para a limpeza. Depois do envio, a próxima edição do campo começa outro retrato.
- **A senha que a pessoa mostra.** O campo que já foi senha nesta página e deixou de ser (`was_password`) só sai como segredo e vira uma entrada do robô (nunca outra credencial do cofre), em todas as edições: a marca não sai mais do elemento. O gravador vê o `type=password` e a máscara por CSS antes dos ouvintes da página (no `pointerdown`, no Tab, no Enter, no espaço fora de um campo e no fim da carga do documento), vê a página tirar o `type=password` (num `MutationObserver`, que responde antes do `focusin` do gravador, também quando a página mostra a senha no próprio `focus` do campo ou no foco pelo teclado) e vê o input que entra no lugar de uma senha que saiu da página, em menos de 1 s, antes ou depois de ela sair (um `<transition>` que põe o input novo antes de tirar a senha, numa tarefa depois): pelo mesmo id ou pelo mesmo `name` e, quando o registro da saída tira um campo só (o "olho" tira uma senha), também pelo mesmo pai ou pelo mesmo lugar (o invólucro que o "olho" recria em volta de um input sem id nem `name`). O registro que tira mais de um campo (a SPA que troca o login inteiro por outra tela no mesmo contêiner, o "olho" que redesenha o formulário) conta pelo mesmo id ou `name` e pela posição: a senha que saiu na posição k de um registro que tirou N campos é o campo da posição k de um registro que pôs N campos no mesmo lugar, em menos de 1 s (o formulário redesenhado sem id nem `name`, com ids novos a cada vez, ou esvaziado e refeito com o mesmo nó do usuário). A procura vem antes do limite de 64 campos guardados que entraram: o "olho" que redesenha um formulário com mais de 64 campos de uma vez também é visto. O campo de texto com o mesmo valor (de 4 caracteres ou mais) de uma senha da mesma raiz também foi senha: o plugin antigo que mostra um gêmeo de texto e esconde o `type=password`, copiando o valor. A procura das senhas também roda numa página com mais de 6000 elementos. A marca só é escrita na gravação quando é verdade: a gravação sem a marca é igual à das versões anteriores, que continuam a lê-la; a que tem a marca elas recusam (nunca a leem sem ela). Além da senha mostrada, o código de uso único mascarado por CSS (`-webkit-text-security`) também leva a marca, mesmo que a pessoa nunca o mostre: o gravador vê a máscara, e o código não conta como senha num campo de texto. A gravação com esse campo também é recusada pelas versões anteriores (falha fechada: nenhum segredo sai, e o campo já sai como segredo pela marca de código). Então a senha que a pessoa mostra com o "olho" antes de pôr o foco no campo, a que a página mostra no foco e a do "olho" que troca o `<input>` de senha por outro, de texto, nunca saem como texto. O campo que já foi senha conta como a senha da página e do grupo: o usuário digitado depois da senha mostrada é o usuário, com as mesmas regras do usuário digitado antes dela, e os outros campos saem da gravação.
- **O rótulo que o componente troca.** Cada retrato guarda os elementos do rótulo do campo (os `<label>` dele e os do `aria-labelledby`). Quando o campo já saiu da página na hora de decidir, o gravador relê esses elementos (e os `<label for>` do id dele na mesma raiz): se agora falam em senha, assinatura ou código, o valor só sai como segredo e vira uma entrada. Os ids do `aria-labelledby` também ficam guardados e são procurados de novo na raiz do campo, junto com os do `aria-labelledby` de agora do campo solto: o componente que aponta o `aria-labelledby` para outro elemento, ou troca o elemento do rótulo por outro com o mesmo id, também é visto. O componente que troca "Valor" por "Assinatura eletrônica" no próprio blur (ou no `pointerdown` do botão) e tira o campo da página não leva mais o valor como texto; o rótulo "Senha" que vira "Valor" continua senha, porque as marcas só sobem.
- **Nada de shadow DOM é embrulhado.** `attachShadow`, `addEventListener`, `composedPath`, `focus` e `blur` continuam nativos. O único nativo que o gravador troca é a propriedade `value` de `HTMLInputElement` e `HTMLTextAreaElement` (`hookValueSetter`, o getter e o setter): o getter só repassa, e o setter só marca o valor que a página muda enquanto a pessoa digita. O `MutationObserver` do gravador (o construtor e o método `observe` guardados antes dos scripts da página: a página que troca `MutationObserver.prototype.observe` não o desliga) fica no documento e em cada shadow root aberto que aparece no caminho de um evento, e só olha o `type` dos inputs e os inputs que entram e saem.
- **Resíduos dos shadow roots.** Shadow roots fechados ficam invisíveis. Um componente que só vira senha depois da decisão do gravador (no `focusout`, num temporizador ou num quadro do blur), com um nome que não fala em senha nem em assinatura, ainda sai como texto. Um componente que formata o valor no blur ("1234" vira "1.234,00") grava o valor formatado; o robô o digita tecla a tecla e a página o formata de novo, e então a conferência do texto digitado falha o passo, sem gravar. Um código em seis caixas de um caractere vira seis passos com o código inteiro, e o site o recusa (falha fechada). O campo que sai da página antes do retrato de depois da última tecla da pessoa (o componente o troca no próprio `input`, por exemplo) é esquecido, e também o que sai sem nenhum `change`, `blur` ou `focusout` que o gravador veja e sem a janela perder o foco (o componente para o `change` e o foco muda por script no mesmo documento); um campo da luz que some no próprio blur quando a pessoa sai para um iframe também. Então o robô fica sem o passo (falha fechada), nunca com um valor guardado antes da última tecla (uma tecla que a página só aplica depois, num temporizador dela, não é vista). O valor que sai antes do blur vai com o descritor desse momento: o campo que só vira senha no próprio blur (ou cujo rótulo só passa a falar em senha, assinatura ou código nele) ainda sai como texto quando o valor sai no `change` (que o navegador dispara antes do blur, quando o componente não o para) ou numa tecla Enter, Tab ou Esc no próprio campo; e o `<label>` em volta do campo que o componente troca por outro (um `<label>` novo, sem `for`) não é relido.
- **Resíduos abertos do gravador.** A senha mostrada ainda sai como texto quando o gravador não vê que o campo foi senha: a máscara por CSS que a página tira sem nenhum `pointerdown`, Tab, Enter ou espaço da pessoa depois de o campo aparecer; o "olho" que troca o input mais de 1 s depois de a senha sair (uma animação longa); o "olho" que redesenha o formulário sem id nem `name` noutro contêiner ou com outra quantidade de campos; o `<transition>` que põe o input novo num registro junto com mais de 64 outros campos e só tira a senha num registro depois (quando a senha sai, o input novo já saiu da lista dos 64 que entraram); o gêmeo de texto cujo plugin não copia o valor da senha; e a troca de `type` ou de input num shadow root aberto por onde nenhum evento passou antes (o `type=password` dele é visto no `pointerdown`, mas a troca do input, não). O componente que troca o `<label>` em volta do campo por outro, no próprio blur, e tira o campo da página ainda leva o valor como texto. Uma senha de operação que não é código, num `type=password` ("Senha do cartão"), vira a senha do login no cofre (uma senha por origem: separar as duas quebraria o "PIN" que é a senha do login).
- **Perdas de disponibilidade do gravador.** Um filtro chamado "Código de transação" vira uma entrada, e a chave da linha com o mesmo valor sai da gravação; o passo nessa linha falha sem agir (o valor é sigiloso, então a chave não pode ficar). O campo que a página reaproveita de "Senha" para outro dado ("Valor (R$)") pede o valor numa entrada em todas as edições, e os outros campos do grupo dele também saem da gravação; o campo de texto que entra no lugar de uma senha que acabou de sair da página (com o mesmo id ou `name` dela, no mesmo pai quando só ela saiu, ou na mesma posição), em menos de 1 s, também, e o campo de texto com o mesmo valor de uma senha da página também. O campo com `autocomplete=username` fora de um login confirmado vira uma entrada, também em logins comuns que a regra não confirma: o login em duas etapas de uma SPA cujo "Continuar" faz um POST de identificação, o login depois do POST do consentimento de cookies, o envio "OK" ou "Prosseguir" e a senha mostrada, digitada e escondida de novo. O código só por um sinal ambíguo fora de um login confirmado com senha vira uma entrada, também na página do segundo fator de uma SPA ("Código", `name="codigo"`, ou "Token", sem `<form>` ou com um botão "Validar"), no `<form>` só com o código sem um login com senha logo antes e na página do segundo fator a que se chega por outro clique (escolher receber o código por SMS) ou sem um login confirmado; o "Token" sozinho que confirma uma operação depois do login (sem `autocomplete=one-time-code`) também. O código de acesso vira uma entrada sempre, também o do segundo fator que se chama "Código de acesso enviado por SMS". A senha nova (`autocomplete=new-password`) vira uma entrada, também no cadastro. O código de uma operação ("Token da transação", "Código de autorização", "Código de verificação do cartão"), também com `autocomplete=one-time-code`, vira uma entrada, nunca o código do cofre. O campo que saiu da página cujo `<label>` a página reaproveita para outro campo que fala em senha ou código vira uma entrada. A SPA que troca o login de dois campos por outra tela de dois campos no mesmo contêiner, em menos de 1 s, faz do segundo campo da tela nova uma senha mostrada (pela posição): ele vira uma entrada, e o outro campo do grupo também. A busca de um campo só que a SPA põe no lugar do login fica com o texto digitado; a troca que demora mais de 1 s não é vista (resíduo acima).
- **Um passo, um elemento.** Edições, marcações e escolhas só se juntam num passo quando são do mesmo campo (a mesma descrição, inclusive o `data-testid`) e do mesmo elemento (o número que o gravador dá a cada elemento): o alvo e o valor de um passo sempre vêm do mesmo elemento.
- **Clique duplo.** O segundo clique (`detail` 2 ou mais, o mesmo seletor) some no passo do primeiro no mesmo elemento e também noutro elemento sem prova de outro alvo (outra chave da linha, outro texto, outro nome, outro rótulo ou outro `data-testid`): o número do elemento sozinho não separa os cliques. Com essa prova, ele só é outro passo quando cada um dos dois cliques gravou algo e o segundo gravou noutro endereço (ou com outro método) que o primeiro: a mesma gravação de novo é o clique duplo num botão que o primeiro clique mudou ("Pagar" que vira "Pagando…", a linha que vira "Processando"), e o robô age uma vez. Resíduos, em que o robô age menos que a pessoa, nunca mais: o clique duplo num botão sem trava que a página recria entre os cliques (cada clique grava) fica um passo só, e o botão de outra linha que sobe para o lugar do que a pessoa clicou, com o mesmo seletor cortado e nada mais diferente ou gravando no mesmo endereço (a linha só no corpo ou na consulta da requisição), também (o robô exclui um onde a pessoa excluiu dois).
- **Limpeza sem caixa.** Os valores sigilosos saem de todo texto que pode chegar ao robô ou ao modelo de linguagem, em maiúsculas ou minúsculas; só os valores digitados, a chave da linha e os endereços são trocados pelo valor exato.

## Regras do executor

As regras completas estão na docstring de `rapa.runner.interpreter`. Na dúvida, o passo grava e falha fechado antes de agir. Em resumo:

- **Rede contra ações repetidas.** Uma ação que grava numa linha (a página e o texto que a escolhe) conta em cada endereço por onde a página principal passa depois dela, até o fim da volta e, depois, até o fim da repetição, menos os que o próprio `navigate` do robô abre. Perdas de disponibilidade conhecidas, que falham fechado: escolher a página por um clique (um link) numa volta seguinte, e uma página aberta por um `navigate` que vai sozinha a outro endereço depois (`replaceState`, `meta refresh`, redirecionamento por script).
- **Confirmação.** A espera pela confirmação do anúncio de um passo que grava tem só o prazo da própria confirmação, nem o do passo nem o da execução: o lançador mata o processo do executor 15 s depois do prazo da execução, e o passo nunca age se esse prazo acabou durante a espera. Depois da confirmação do aviso de passo irreversível, o alvo, a linha única e a rede são conferidos de novo, na mesma página da primeira conferência; se a página for outra, o passo falha sem agir. Perda de disponibilidade aceita: uma página que sai e volta ao mesmo endereço durante essa espera também é recusada, porque a volta conta como da ação anterior na mesma linha.
- **Agir no elemento conferido, na hora de agir.** Um passo que grava age no elemento que foi conferido, nunca no que o localizador encontrar depois em outro documento. A espera pelo elemento (visível, habilitado e parado; editável para digitar; a opção na lista) vem antes, sem mandar nenhuma entrada à página. Depois dela, o contador de navegações da página principal (de outro documento e do mesmo documento: `pushState`, `replaceState`, `#`), a página e, numa linha escolhida pelo texto, a linha única com o elemento dentro dela são conferidos de novo. A ação vai sem `force`: o Playwright ainda confere que o alvo não está coberto, também por outro documento (um iframe por cima do botão, a página por cima de um iframe), nem inerte (um diálogo modal), e espera ficar livre. Um vigia na fase de captura da janela confere o primeiro evento da ação; o ouvinte dele é posto em cada documento antes de qualquer script da página, então decide antes dos ouvintes dela, também dos que ela põe na janela; como `document.open()` (também o `document.write` depois de a página carregar) tira da janela os ouvintes dela, cada vigia põe de novo o seu. Se o evento não cai no alvo, se o endereço mudou, se a linha não tem mais um elemento cujo texto inteiro é a chave (a linha reaproveitada de "12" para "120" não vale) ou, num clique ou numa marcação, se o rótulo do alvo (`aria-label`, `title`, o texto de `aria-labelledby` e dos `<label>` dele, `data-testid` e o texto, com o `alt` das imagens, o valor dos campos de dentro e o que a página pôs num `<slot>` (o botão de dentro de um web component); no elemento do `aria-labelledby`, também o `aria-label`, o `title`, os nomes de dentro dele e, num campo, o valor ou a opção escolhida; no `<label>`, também o `aria-label`, o `title` e o `aria-labelledby` dele; e os nomes dos elementos de dentro: o `aria-label` de um `<svg>`, o nome do `aria-labelledby` deles e, sem um nem outro, o `title` de um ícone, de uma imagem sem `alt` ou de um texto `aria-hidden`; os `<label>` contam com os nomes de dentro deles) não é mais o da hora em que o vigia foi posto (uma lista virtual que reaproveita o botão para outro item enquanto o Playwright rola até ele; vale a dica que a página põe quando o mouse chega ao alvo, se o rótulo de antes da chegada era o da hora do vigia: o `title` que sai ou chega e o `aria-label` que chega igual ao `title` da chegada (como no Bootstrap 5), sem que um ou outro tenha passado por outro valor desde o vigia (o nó reaproveitado antes de uma dica do jQuery UI tirar o `title` passa pelo nome do outro item), com o texto, os `<label>`, o `aria-labelledby` e o `data-testid` iguais, e os nomes de dentro iguais ou chegando com o `title` e o `aria-label` do alvo iguais; o texto que muda, como o "Seguindo" que vira "Deixar de seguir", é o sinal de um nó reaproveitado), a ação inteira é cancelada e o passo falha sem agir (`elemento_ambiguo`). Um clique cujos eventos não chegam à janela do alvo foi entregue a outro documento por cima dele: o passo falha (`elemento_ambiguo`) dizendo que o clique pode ter feito outra coisa. Num iframe deslocado ou em escala por uma transformação (o modal centralizado com `translate(-50%,-50%)`), o Playwright não confere o que está por cima do alvo: o clique ou a marcação espera, só lendo a página, que o alvo fique livre (abaixo). Num clique, numa marcação ou numa escolha, o vigia também confere que os campos digitados do mesmo documento ainda têm o valor que a releitura leu: a página que troca o logradouro enquanto o clique espera uma camada de "buscando CEP" sair faz o passo falhar sem agir (`acao_falhou`). O vigia só lê os campos do documento do alvo: com campos digitados noutro documento (o logradouro na página principal e o Salvar num iframe), o clique ou a marcação espera, só lendo a página e rolando o alvo para a janela como o Playwright (sem animação, também com `scroll-behavior: smooth`), que o alvo fique livre no documento dele e nos documentos da mesma origem acima dele (uma camada com `pointer-events: none` ou `inert` conta como coberta; o texto de um botão que vem de um `<slot>` sobe pelo slot; a caixa do alvo vai para o documento de cima pela caixa do iframe, também deslocada ou em escala, também através de shadow roots, cortada pela janela de cada documento, e o ponto é o centro dela; o alvo fora da janela do documento dele ou de um de cima, como numa gaveta que ainda entra, conta como coberto; um alvo sem caixa própria, como um link ou um botão com `display: contents`, conta como coberto, porque o Playwright clica no meio do primeiro pedaço desenhado dele, que pode ser um texto, um `::before`, um `::after` de dentro ou o shadow root fechado de um componente; num iframe, uma caixa do alvo que passa da janela do iframe também conta como coberta, porque o Playwright a corta só pela janela de cima e o clique pode cair fora do iframe), e só então os campos são relidos; se o alvo continua coberto quando falta menos de 1 s do prazo do passo, o passo falha sem agir (`tempo_do_passo_esgotado`). Num iframe girado, inclinado ou em perspectiva que muda o plano dele, onde o ponto não se traduz, a espera continua (uma animação de entrada) e, no fim do prazo, o passo falha sem agir (`acao_falhou`); a rotação de zero grau e a perspectiva que não muda o plano (`perspective(1px) translateZ(0)`, contra o borrão do texto) não contam. Com o vigia já posto, o elemento conferido de um clique, de um download ou de uma marcação ainda precisa ser o único que o localizador encontra (a rolagem da espera, ou um feed que põe um item no topo, pode ter feito a página reaproveitá-lo para outro item; o que ela redesenha depois do vigia troca o rótulo que ele guardou; toda marcação passa por essa conferência, também a de uma caixa que já estava como devia: o nó reaproveitado pode mostrar um item no outro estado, e a marcação clicaria nele, ou outro item já como devia, e o passo daria certo sem o item pedido), senão o passo falha sem agir (`elemento_ambiguo`). Um primeiro evento que chega mais de 0,5 s depois do vigia (o Playwright esperou algo que essa espera não vê, como uma página de outra origem por cima do iframe do alvo, ou uma camada que chegou logo depois dela) é recusado (`acao_falhou`). Marcar uma caixa que já está como deve ficar não manda evento nenhum e não é recusa. Um botão montado de novo na mesma linha durante a espera, sem navegação, leva a uma nova conferência completa, uma vez; na segunda vez, ou se a página trocou de documento durante a espera, o passo falha sem agir (`acao_falhou`). Perdas de disponibilidade aceitas: qualquer mudança de endereço da página principal entre a conferência e a ação (também um filtro que muda a consulta do endereço), uma tecla para um elemento que não recebe o foco, uma linha cuja célula da chave ganha texto quando o mouse passa por cima (um ícone de editar), um botão cujo texto muda com o mouse em cima ou no clique (o "Seguindo" que vira "Deixar de seguir", o "Salvando..." no `pointerdown`), um botão cujo rótulo muda num ouvinte do `mousemove` ou que mostra uma contagem que muda sozinha (um cartão com o progresso, um contador de não lidas no `aria-label` de dentro), um ícone de espera com nome posto no `pointerdown`, a foto de um cartão cujo `alt` troca com o mouse em cima, a dica do jQuery UI num ícone de dentro com `title` (também num texto de dentro com `title` e no `title` de um `<label>` em volta da caixa), a dica do Tippy com `aria-labelledby`, a dica que tira o `title` de um ícone de dentro, a ajuda que põe o `title` num texto cortado de um botão com outro nome de dentro, um ponto de aviso cujo `title` muda sozinho, um link ou um botão com `display: contents` e um alvo mais alto que o iframe dele (os dois com campos digitados noutro documento ou num iframe transformado), e, com campos digitados noutro documento, uma lista virtual que reaproveita o botão quando a espera rola até ele. Com `zoom` do CSS em volta de um iframe transformado, o Playwright erra o ponto do clique (põe as caixas sem o zoom) e o clique poderia cair na página de cima: o alvo conta como coberto, e o passo falha sem agir. Fora da espera ficam também os cliques que falham em todas as versões: um iframe cujo contêiner usa `translate` e `scale` como propriedades soltas (o Playwright só lê `transform`), uma lista que recria os nós a cada rolagem num iframe deslocado e um botão sob um rodapé fixo no fim da página.
- **Texto conferido.** Depois de digitar um texto, o valor do campo é conferido. Se a página mudou o campo, o texto é digitado de novo, e vale se o campo ficar com ele ou exatamente com o que ficou da primeira vez (a máscara da própria página); senão, o passo falha. Num passo que grava, nada é digitado de novo: vale o texto como o navegador o guarda (posto numa cópia solta do campo: `\r\n` vira `\n`, um e-mail perde os espaços das pontas), com os brancos (e o espaço rígido) normalizados, ou, num texto sem letras, a máscara da página: os mesmos dígitos na mesma ordem (CPF, CNPJ, CEP, telefone, data, centavos), com o sinal de menos, e, num número com casas decimais ou com o ponto dos milhares, o mesmo número ("1234,5" pode virar "R$ 1.234,50"; "10,5" que vira "1,05" e "1.234,00" que vira "123.400,00" não valem). Um campo vazio nunca vale por um texto, e num `input[type=number]` a regra dos dígitos não vale. O texto que só mudou de brancos também vale, e um inteiro pode ganhar casas decimais zeradas ("10" vira "10,00"); maiúsculas trocadas não valem. Qualquer outra diferença, como o `maxlength` que cortou o texto ou uma página que troca letras, faz o passo falhar. Os valores do campo nunca vão para eventos nem mensagens.
- **Campos digitados, lidos de novo antes de gravar.** Os campos de texto que o robô digitou são lidos de novo antes de cada passo que grava e age na página e comparados com a referência deles: o valor da digitação, ou o do fim do último clique, tecla ou escolha do robô. O que muda durante esses passos vale (a sugestão escolhida num autocompletar, a busca que a página limpa depois do Enter), mas só para os campos que ainda tinham a referência logo antes de o passo agir: o campo que a página já tinha mudado (durante uma espera) fica com a antiga. A formatação que a página põe quando o foco sai do campo vale pela comparação (brancos, máscara, "10" que vira "10,00", "10.00" ou "10,00 €"; nunca "10,00 mil" nem "D 10.00", e antes das casas zeradas só o sinal, um símbolo de moeda e o ponto dos milhares; nunca um número negativo que não foi digitado: o sinal de menos antes do primeiro dígito, também o U+2212, os traços e as outras formas do hífen, os parênteses em volta e o sinal depois do último dígito; e nunca o traço do preço sem centavos, "10,-" ou "CHF 10.–", que pode ser positivo ou negativo); o que a página muda sozinha enquanto o robô espera ou digita noutro campo, também depois de um `pushState` ou `replaceState` (uma consulta de CEP que responde depois), faz o passo falhar sem agir (`acao_falhou`). Um campo digitado de novo vale pela última vez, e um que saiu da página (ou cujo documento acabou) deixa de contar; cada campo é lido no próprio documento, também num iframe. Fora da conferência antes de gravar, a leitura dos campos tem um prazo curto: numa página travada, nenhum ganha referência nova. Resíduos: a mudança que chega durante um clique, uma tecla ou uma escolha do robô vira a referência (também a que chega enquanto um passo que só lê, como abrir uma aba, espera uma camada sair), e a que chega entre a releitura e a ação de um passo de digitar ou de teclar (ou, num campo de outro documento, até 0,5 s depois da releitura) não é vista. A comparação aceita as máscaras de centavos, então "10" que vira "1,0" também vale; e, pela regra dos dígitos ou pela dos números com casas decimais, também valem um "D" de débito ("10 D", "10,50 D"), uma palavra de escala ("10 mil", "10K"), colchetes em volta do número e um sinal de menos seguido de um caractere invisível. Perdas de disponibilidade aceitas: um campo digitado que a página reescreve quando o mouse chega ao botão, ou que ela monta de novo com o mesmo valor enquanto o clique espera, faz o passo falhar; um código com hífen antes dos números ("OS-12345") conta como negativo, uma unidade com letras depois das casas zeradas ("10,00 kg") ou uma moeda fora da lista antes delas ("¥10.00") não vale, e o preço sem centavos ("10,-") nunca vale.
- **Resíduos conhecidos.** A conferência da linha única não vê shadow roots fechados nem uma chave que só o CSS mostra, sem nada no HTML (o `content` de um `::before`); uma lista virtual que troca o que a linha é sem trocar o texto dela também não é vista. O ouvinte do vigia é posto antes dos scripts de cada documento (também num iframe sem endereço); num documento reescrito por `document.open()`, o vigia o põe de novo na hora de agir, depois dos que a página pôs na janela desde então, que veem o evento antes dele (num iframe de outra origem que se reescreve, o clique que espera a página de cima pode chegar a eles e o passo dizer que nada foi feito, como nas versões anteriores). Num iframe com `sandbox` sem `allow-scripts`, nenhum ouvinte roda: o vigia não recusa nada ali, e um clique que grava falha dizendo que pode ter feito outra coisa. Um ouvinte da página no próprio alvo ou num elemento em volta dele vem depois do vigia. Num iframe girado ou inclinado sem campos digitados noutro documento, ou num iframe de outra origem deslocado, o clique fica com o Playwright, que não confere o que está por cima do alvo: o passo falha dizendo que ele pode ter feito outra coisa; se o que estava por cima levou a página principal a outro endereço (a janela do alvo acabou), o vigia não tem o que ler e o passo dá certo sem o clique ter chegado ao alvo, e uma marcação que foi para outro documento falha com `acao_falhou` sem dizer que algo pode ter sido feito. O rótulo depois da chegada do mouse só vale quando só a dica mudou: uma lista que reaproveitasse o nó na chegada do mouse para um item cujo botão de ícone não tem nome nenhum (o `title` que sai, como a dica do jQuery UI) não seria vista. O conteúdo de `::before` e `::after` (`content: attr(...)`) não entra no rótulo. Depois do primeiro evento de um clique ou de uma marcação, e até o `click`, o vigia confere de novo o endereço, a linha e o rótulo em cada evento do navegador: se a página os mudou com os eventos de antes (no `pointerdown`, no `mousedown`, no `pointerup` ou no `mouseup`), ele interrompe o clique e o passo falha (`elemento_ambiguo`) dizendo que esses eventos chegaram à página. No `click`, o vigia sai antes dos ouvintes da página: uma página que troca a linha num ouvinte do `click` na janela, antes do ouvinte do botão, não é vista (como nas versões anteriores). Um segredo vai para o elemento em que a origem foi conferida, sem o vigia.

## Regras da gravação ao vivo (Demonstrar e Generalizar)

As regras completas estão nas docstrings de `rapa.session.host`, `rapa.session.egress`, `rapa.session.keys`, `rapa.control.sessions.service`, `rapa.control.sessions.launcher`, `rapa.control.sessions.relay`, `rapa.control.api.sessions` e `rapa.compiler.review`, e no cabeçalho de `rapa/ui/static/ao_vivo.js`. Em resumo:

- **O hospedeiro.** Cada sessão é um processo `python -m rapa.session.host` com um Chromium sem janela, num perfil novo (pasta temporária 0700), e o gravador (`rapa.recorder.Recorder`) ligado ao contexto. A configuração e o token chegam pela entrada padrão, nunca pela linha de comando. Ele serve um websocket local que só aceita o plano de controle (`Authorization: Bearer <token>`, comparação em tempo constante, uma conexão por vez) e por onde saem as imagens da tela (o screencast do CDP, em JPEG do tamanho da área visível, cada quadro confirmado ao navegador e os intermediários descartados sob pressão), o endereço e o título da página, e entram mouse, roda, teclado (o texto por `Input.insertText`, para acentos, teclas mortas e IME; um caractere do teclado americano como tecla, como faz o Playwright), tamanho, navegação (só http e https) e respostas a diálogos da página. No `parar`, devolve a gravação já limpa pelo gravador e sai. Sem entrada por 10 minutos (`RAPA_SESSAO_OCIOSA_S`) ou com 60 minutos (`RAPA_SESSAO_MAX_S`), encerra sozinho e nada é guardado. Use o Chromium completo (`RAPA_CHROMIUM_PATH`, por exemplo `/usr/bin/chromium`): o `chrome-headless-shell` ignora a política do WebRTC (o script que tira o WebRTC das páginas ainda vale nele).
- **A guarda da saída.** O navegador da sessão roda na máquina (ou no pod) do plano de controle, então toda conexão TCP dele passa por um proxy SOCKS5 dentro do hospedeiro (`rapa.session.egress.EgressGuard`; o Playwright põe `<-loopback>` e, sem regras do operador, `MAP * ~NOTFOUND`): navegações, os saltos de um redirecionamento (o `route` do Playwright não os vê), iframes, `fetch`, workers, websockets, downloads e o TCP do WebRTC. A guarda resolve o nome ela mesma, recusa (resposta SOCKS 0x02) se qualquer endereço for da própria máquina (loopback, `localhost`, `*.localhost`), link-local (o metadata da nuvem em `169.254.169.254`, o ECS e o Pod Identity), `0.0.0.0/8`, não especificado, multicast, `fd00:ec2::/32` (o IMDS e o Pod Identity da AWS em IPv6), `100.100.100.200`, qualquer endereço desta máquina fora do loopback (o IP do pod ou da máquina da API, onde um serviço que escuta em `0.0.0.0` também responde; vale o endereço que aceita `bind` aqui) ou um IPv6 que carrega um desses IPv4 (mapeado, compatível, NAT64 ou 6to4), e conecta exatamente ao endereço conferido (sem troca de DNS no meio). Só aceita o método sem autenticação e o CONNECT (BIND e UDP ASSOCIATE recebem 0x07), com prazos para o aperto de mão (10 s), a resolução (10 s) e a conexão (30 s), e no máximo 256 conexões ao mesmo tempo; quando um lado fecha, o outro tem 60 s para terminar; ao fim da sessão, derruba as que restam. Os argumentos de proxy do operador em `RAPA_ARGS_NAVEGADOR` (`--proxy-server`, `--no-proxy-server`, `--proxy-pac-url`, `--proxy-auto-detect`, `--proxy-bypass-list`) são tirados do navegador da sessão: o Chromium obedece ao último, e eles desligariam a guarda. O hospedeiro termina sozinho quando o processo que o abriu morre (a API caiu), fechando o navegador e apagando o perfil. O UDP fica fora do navegador: `--disable-quic`, `--webrtc-ip-handling-policy=disable_non_proxied_udp` e, em todo documento (também iframes e janelas novas), um script que tira o `RTCPeerConnection` das páginas. Nenhum `--disable-features` é acrescentado: o Chromium só obedece ao último, e ele desfaria a lista do Playwright. Os nomes mapeados pelo operador em `--host-resolver-rules` (`MAP nome endereço`, como os portais de teste em `*.rapa.test`) valem como mapeados, mesmo para o loopback: é configuração do operador, nunca da pessoa. Um endereço inicial interno é recusado já na criação da sessão (422), e a pessoa recebe um aviso quando a página dela falha por causa da guarda.
- **O resíduo da rede privada.** As redes privadas (10/8, 172.16/12, 192.168/16, fc00::/7) continuam abertas, porque os portais de intranet são o caso de uso. As sub-redes do banco, da API do Kubernetes e dos outros serviços do plano de controle **precisam** ser fechadas no deploy, pela NetworkPolicy do pod do navegador ou por um proxy de saída (PR E).
- **Os atalhos.** Só os atalhos de edição chegam ao navegador da nuvem (`rapa.session.keys.key_commands`): Ctrl ou Meta com A, C, V, X, Y e Z (Shift só com V e Z), as teclas especiais com Ctrl e Shift, Alt+setas (voltar e avançar) e F5. Tudo o que é comando do próprio Chromium cai: Ctrl+T, Ctrl+N, Ctrl+H, Ctrl+J, Ctrl+U, Ctrl+O, Ctrl+Shift+I, qualquer Alt ou Meta com outra tecla (Alt+Home abre a página inicial), F1 a F12 menos o F5, Shift+Esc e Ctrl+Shift+Delete. Mesmo assim, uma aba com página interna (`chrome:`, `file:`, `view-source:`, `devtools:`...) nunca vira a da pessoa: fecha sem que nenhum quadro ou evento `pagina` dela saia.
- **O perfil.** O lançador cria uma pasta só da sessão, com o perfil dentro, e a apaga quando o processo do hospedeiro sai, de qualquer jeito: num SIGKILL (o fim do prazo de encerramento, a falta de memória) o hospedeiro não apaga nada, então o lançador mata o Chromium que ainda tenha o perfil na linha de comando e apaga a pasta, tentando de novo por até 10 s. Os cookies do portal demonstrado nunca ficam no disco.
- **O lançador.** `SessionLauncher` tem `start(job) → endereço e token`, `stop`, `terminate` e `is_alive`. `stop` vem depois do `parar` e espera o hospedeiro sair sozinho (até 15 s); `terminate` encerra na hora (SIGTERM, e SIGKILL depois de 10 s) um hospedeiro que ninguém mandou parar: o prazo, o navegador perdido, o fim do serviço (que encerra todos ao mesmo tempo). O `LocalSessionLauncher` roda o hospedeiro num subprocesso com o ambiente mínimo do executor (`rapa.control.launcher.child_env`) e guarda o token só em memória; o banco nunca o vê. O prazo máximo também é garantido de fora. Na Fase 1, um lançador de pods entra no lugar dele sem mudar o protocolo.
- **Quem pode.** Só quem tem o papel de criação na área abre uma sessão (`Principal.has_role`, a função única das permissões). Só a dona da sessão, e enquanto tiver esse papel na área, a vê, recebe bilhete, assiste, para e revisa; para qualquer outra pessoa (outra área, outra empresa, o administrador) a sessão não existe. A empresa vem sempre do token. A versão criada a partir da revisão é da dona, que por isso nunca a aprova.
- **O bilhete.** O navegador da pessoa não recebe o token de acesso. A interface pede à API (`POST /v1/sessoes/{id}/bilhete`) um bilhete aleatório que vale 60 s e uma vez só, para uma sessão, e o `ao_vivo.js` abre `WS /v1/sessoes/{id}/ao-vivo` **sem nada no endereço** e manda o bilhete como a primeira mensagem (`{"tipo": "bilhete", "bilhete": "..."}`): assim ele nunca aparece no log de acesso do servidor nem de um proxy. Um endereço com consulta (`?bilhete=`) é recusado antes de abrir (HTTP 403); sem um bilhete válido na primeira mensagem em 5 s (inválido, vencido, já usado, de outra sessão ou de outra empresa), o websocket fecha com o código 1008, sem dizer por quê. Com `RAPA_PUBLIC_URL` (e as origens extras de `RAPA_ORIGENS_AO_VIVO`, para uma interface servida noutro endereço), o `Origin` do websocket precisa ser o da interface (HTTP 403 se não for); um cliente fora do navegador, sem `Origin`, depende só do bilhete. Sem nenhuma das duas configurações, o `Origin` não é conferido. Os bilhetes ficam só na memória do processo, pelo SHA-256, e nada os registra. Se a conexão cair, o JavaScript pede outro bilhete e reconecta uma vez.
- **O repasse.** O plano de controle mantém uma ligação com o hospedeiro por sessão e repassa os quadros e os eventos para a janela e as entradas para o hospedeiro. Da janela, só passam as mensagens de entrada válidas, conferidas de novo; `parar` só pelo REST, que guarda a gravação e audita. Uma janela por vez: uma segunda janela da mesma dona **substitui** a primeira (que recebe `fim` com o motivo `substituida` e o código 4001), e nada do que a janela antiga ainda mandar passa. Sem fila: numa rede lenta, só o quadro mais novo espera, e os eventos vão por uma caixa de saída da janela (no máximo 64, e um `pagina` ou `tela` novo toma o lugar do que ainda não saiu): uma janela que para de ler nunca trava a ligação com o hospedeiro, e o `parar` funciona mesmo assim. Um segundo `parar` ao mesmo tempo recebe 409 e não estraga o primeiro.
- **Os diálogos da página.** Um `alert`, `confirm` ou `prompt` do portal aparece dentro da tela ao vivo, num quadro escrito "Mensagem da página aberta no navegador da gravação (não é do RaPA)", com o texto da página como texto puro; nunca como diálogo nativo do navegador da pessoa, que sairia com o nome do RaPA e deixaria a página fingir ser o RaPA para pedir uma senha.
- **As vagas.** As sessões usam a reserva interativa ("10% das vagas ficam reservadas para gravação, controle ao vivo e testes"). Uma sessão só abre se as sessões abertas de todas as empresas e as validações rodando somam menos que `RAPA_SESSOES_MAX` (padrão: o tamanho da reserva, de `platform_settings`); o despachante conta as sessões abertas do mesmo jeito, então sessões e validações juntas não passam da reserva. Para ninguém tomar todas as vagas, uma empresa tem no máximo `min(RAPA_SESSOES_POR_EMPRESA, max(1, RAPA_SESSOES_MAX // 2))` abertas (contadas no banco sob trava): com 30 navegadores (reserva 3), uma por empresa; só com uma reserva de uma vaga uma empresa ainda ocupa a única. Contar a plataforma inteira precisa do papel do despachante (`RAPA_DISPATCHER_DATABASE_URL`, no mesmo processo); sem ele, a API conta só as sessões dela. Encerrar uma sessão vencida nunca acontece sob a trava das aberturas.
- **Quem segura a sessão.** Cada linha guarda o processo da API que segura o navegador (`instance_id`), e ele renova `seen_at` a cada varredura (15 s, a primeira na subida). Na subida e em toda varredura, a API encerra as sessões abertas, de qualquer empresa, que ninguém renova há mais de 2 minutos (a API que as abriu caiu): com uma réplica, todas as de antes da queda; com várias, só as das réplicas que pararam. Ler a sessão de outra réplica viva não a encerra.
- **Os dados.** `recording_sessions` (área, dona, endereço sem a consulta e o fragmento, que podem ter um token, situação, prazos, o processo que a segura e o rascunho criado) e `recordings` (o JSON do gravador, imutável) têm a empresa liderando as chaves e isolamento por linha. Só o navegador da nuvem recebe o endereço inteiro. Uma trava impede trocar a empresa, a área, a dona, o endereço, o processo e os prazos, reabrir uma sessão encerrada ou parada, voltar de rascunho para parada e mudar o robô e a versão fora da criação de um rascunho (a versão de um mesmo robô só avança e precisa existir). A aplicação nunca apaga nada, e o despachante só lê a situação das sessões. Abrir, parar e criar o rascunho entram na auditoria encadeada da empresa.
- **Generalizar.** As propostas vêm da compilação determinística da gravação (as entradas de `generalize_inputs` e as repetições de `rapa.compiler.repetition`: passos seguidos feitos de novo com outros valores viram um `for_each` sobre uma entrada de lista) e, com o hub de pé, do modelo (`propose_edits`). Cada operação do modelo é conferida pelo código, uma a uma; as recusadas aparecem com o motivo. Sem o hub, as sugestões das regras continuam, com um aviso claro. Nada entra sem a pessoa aceitar: a tela começa tudo em "Rejeitar", o título e a descrição do formulário são os da compilação e os do modelo aparecem à parte (aceitar os põe nos campos), e o rascunho aplica só o que foi aceito, pelas operações fechadas de `rapa.core.edits` e pelo serviço de robôs (validação e portão de política de sempre). Uma escolha que o código não consegue aplicar volta como erro, nunca some.
- **Resíduos conhecidos.** O token do canal, os bilhetes e a ligação com o hospedeiro ficam no processo que abriu a sessão: com várias réplicas da API, a sessão só é controlada pela réplica que a abriu (o lançador de pods resolve isso na Fase 1). Um "parar" que chega a outra réplica recebe 409 e não encerra a sessão, e a réplica que segura o navegador o fecha quando a sessão deixa de estar aberta no banco. A idade de `seen_at` é medida pelo relógio de cada réplica: com uma réplica atrasada mais de 1 min 45 s, as outras encerram as sessões dela (os relógios precisam de NTP). A origem configurada em `RAPA_PUBLIC_URL` é comparada sem o usuário e sem a porta padrão, como o navegador a manda. As redes privadas ficam com a NetworkPolicy do deploy (acima). O modelo não propõe repetições (o conjunto fechado de edições não tem essa operação): elas vêm só das regras. Uma sessão que termina sozinha perde o que foi demonstrado.

## Regras de Publicar (agenda, webhook e lote por planilha)

As regras completas estão nas docstrings de `rapa.core.cron`, `rapa.control.services.schedules`, `rapa.control.services.webhooks`, `rapa.control.services.batches`, `rapa.control.services.sheets` e da migração `v0004_agendas_webhooks_lotes`. Em resumo:

- **Quem pode.** Qualquer papel na área do robô vê as agendas, os webhooks e os lotes dele; só quem opera ou administra a área (`can_automate`, que passa por `Principal.has_role`) cria, muda, troca a chave e remove. Para outra área e outra empresa, nada disso existe (`NotFound`). A empresa vem sempre do token; a entrega de um webhook, sem token, só descobre a empresa pelo próprio webhook.
- **Uma porta de entrada para as execuções.** Agendas, webhooks e lotes criam execuções por `enqueue_run` e `enqueue_many` (`rapa.control.services.runs`), como o REST, o MCP e a interface: a mesma trava de inícios da empresa, o mesmo limite da fila, a auditoria de cada execução e a prioridade do plano (`PRIORITY_BY_TRIGGER`: interativo 0, MCP, REST e interface 1, agenda e webhook 2, lote 3). Cada origem tem o seu escopo de idempotência (`agenda`, `webhook`), então uma chave do REST nunca alcança a de uma ocorrência ou de uma entrega. Nada é repetido sozinho: uma execução de agenda, webhook ou lote que falha fica como falhou, e as regras de `write_started_at` da fila valem para todas.
- **Agendas.** A agenda é do robô e roda a versão publicada no momento de cada ocorrência, como o REST e o MCP; as entradas fixas são conferidas pelo esquema dessa versão a cada ocorrência. O cron é o de 5 campos do Vixie (dia do mês ou dia da semana quando os dois estão restritos), na hora local do fuso (`America/Sao_Paulo` por padrão): um horário que não existe roda uma vez, no fim do pulo do relógio, e um que se repete roda uma vez, na primeira passagem. O despachante dispara as agendas numa etapa do próprio laço (`Scheduler`, a cada `RAPA_AGENDA_INTERVALO_S`): acha as vencidas pelo papel do despachante (que só lê a fila delas), revezando as empresas (a mais atrasada de cada uma, depois a segunda de cada uma: uma empresa com milhares de agendas vencidas não empurra as das outras para depois da tolerância), e trata cada uma numa transação fixada na empresa, pelo papel da aplicação, com a linha travada (`FOR UPDATE SKIP LOCKED`). Cada volta do agendador dura no máximo meio segundo (`Scheduler.max_tick_s`, contado depois da busca das vencidas: uma busca lenta não faz a volta disparar só uma agenda), para não atrasar o despacho das execuções, que vem logo depois no mesmo laço; quando sobram agendas vencidas, a volta seguinte começa sem esperar o intervalo, com o despacho rodando entre uma e outra. Só fica para trás a volta que disparou alguma agenda: uma volta cheia em que outro despachante já tinha travado todas espera o intervalo, sem girar à toa. Uma empresa tem no máximo `RAPA_AGENDAS_POR_EMPRESA` agendas ligadas (200 por padrão; contadas sob trava ao criar ou ligar; acima disso, 409). A ocorrência é única por agenda e horário (chave primária): com dois despachantes, uma ocorrência nunca vira duas execuções. Se `next_run_at` passou de `RAPA_AGENDA_TOLERANCIA_S` (o serviço ficou fora do ar), tudo o que passou da tolerância vira **um** registro `perdida` (no horário da primeira, com a primeira e a última na auditoria) e a conta recomeça em agora menos a tolerância, sem uma linha por ocorrência perdida; das que estão na tolerância, só a mais nova roda (as outras, `substituida`); e também ficam registradas, sem rodar, as de robô não publicado, entradas que não valem mais, execução anterior da agenda ainda em andamento (uma agenda nunca se sobrepõe a ela mesma) e fila cheia. Ligar uma agenda desligada conta a partir de agora; remover só arquiva. O cron só aceita dígitos ASCII.
- **Webhooks.** A chave de assinatura aparece uma vez (na criação e na troca, com `Cache-Control: no-store`) e nunca vai para o banco, para o log nem para a auditoria: o banco guarda um sal aleatório, e a chave é `HMAC-SHA256(RAPA_CHAVE_WEBHOOKS, empresa ‖ webhook ‖ versão ‖ sal)`. A assinatura (`X-RaPA-Signature: sha256=<hex>`) cobre `<X-RaPA-Timestamp>.<X-RaPA-Delivery>.<corpo>`: o identificador da entrega entra nela, senão quem copiasse uma entrega válida a repetiria com outro identificador. O horário só tem dígitos e o identificador (1 a 200 caracteres ASCII visíveis) **não tem ponto** (a expressão do código e o `CHECK` da migração 0004): com um ponto, dava para mover a fronteira entre o identificador e o corpo sem mudar a assinatura. Comparação em tempo constante; horário a até 5 minutos do servidor; webhook desconhecido, removido, assinatura errada e horário fora da tolerância dão a mesma resposta (401). A mesma entrega de novo devolve a mesma execução (202), com outro corpo é conflito (409). O limite por webhook (`rate_per_minute`) conta só as entregas com assinatura válida. Antes de ler o webhook no banco, a entrega passa por `WebhookGate`, na memória do processo: um identificador que o banco disse não existir (ou estar removido) é respondido com 401 por um minuto sem ir ao banco; cada endereço de origem (IPv4 como veio, IPv4 dentro de IPv6 como o IPv4, IPv6 pela rede /64, que é o que um cliente costuma ter inteira) tem um balde gasto só pelas entregas recusadas na assinatura (60 por minuto), e sem fichas recebe 429 enquanto o balde do processo estiver abaixo da metade (com o processo folgado, um endereço sem fichas ainda passa: o balde é para proteger o banco, não para punir quem compartilha um NAT); e o processo inteiro lê no máximo `RAPA_WEBHOOKS_POR_SEGUNDO` webhooks por segundo (200 por padrão, com folga do dobro), acima disso 429. Um webhook que já passou do próprio limite (`rate_per_minute`) recebe 429 antes desses baldes, sem gastar nada deles. Atrás de um proxy, o servidor precisa ver o endereço do cliente: `FORWARDED_ALLOW_IPS` do uvicorn com o endereço ou a rede do proxy (nunca `*`, que deixaria qualquer cliente escolher o próprio endereço no `X-Forwarded-For`), senão todos dividem o mesmo balde. O corpo tem até 64 níveis de objetos e listas, conferidos antes de ler o JSON. O corpo são as entradas do robô, conferidas pelo validador de sempre (422 para campo a mais ou a menos, sem repetir valores). Para ler o webhook antes de saber a empresa, a política de `webhooks` deixa uma transação **sem empresa** ver só a linha do identificador em `rapa.webhook_id` (`Database.webhook_lookup_session`); nada se grava assim.
- **Lotes.** A planilha (xlsx ou CSV, até `RAPA_LOTE_MAX_BYTES` e `RAPA_LOTE_MAX_LINHAS`) nunca é guardada, só o resumo dela. Fórmulas são recusadas (nada é calculado nem lido do cache de uma fórmula), assim como células com erro, macros e bombas de zip; o xlsx é lido pelo `openpyxl` com o `defusedxml`. A leitura tem limites que não dependem do que o arquivo declara: a `<dimension>` da aba é ignorada (`reset_dimensions`), cada linha para uma coluna depois do limite, a leitura para depois de `RAPA_LOTE_MAX_LINHAS` mais 10 mil linhas vazias (também no CSV), só as linhas com algo ficam na memória, no máximo 64 abas (cada uma num arquivo, nenhuma de gráfico) e cada parte que o `openpyxl` monta inteira (estilos, pasta de trabalho, relações, propriedades, abas de gráfico) tem até 1 MiB descompactada e, somadas com as relações de todas as abas, até 2 MiB; a primeira aba e os textos compartilhados são percorridos antes pelo `expat`, sem montar nada, para recusar linhas e células demais ou um texto enorme antes do `openpyxl`; só as abas e os textos compartilhados, lidos aos poucos, entram no limite total de 64 MiB. As colunas casam com as entradas pelo nome técnico ou pelo título (ou por um mapa explícito); toda linha é convertida e conferida antes de criar qualquer coisa, e com um erro (ou sem espaço na fila para todas) nada é criado. As execuções do lote usam a mesma versão; o andamento é a soma das situações delas. O resultado traz só as saídas que o robô declara, nunca as entradas, e nada dele vira fórmula no Excel: no CSV, todo campo vai entre aspas e um gatilho de fórmula (`=`, `+`, `-`, `@`, tabulação, retorno) no começo do campo ou logo depois de um `;`, `,`, tabulação ou quebra de linha ganha um apóstrofo antes (nem um Excel que separa por vírgula abre uma célula com fórmula); no xlsx, tudo é texto, sem os caracteres de controle que o XML não aceita. A tela Lotes aceita o mesmo tamanho de planilha do REST (`RAPA_LOTE_MAX_BYTES`, no `ui.upload` e no limite do corpo do envio de arquivo do NiceGUI).
- **Os dados.** `schedules`, `schedule_occurrences`, `webhooks`, `webhook_deliveries`, `batches` e `batch_rows` têm a empresa liderando as chaves e isolamento por linha (ENABLE e FORCE). Travas impedem trocar a empresa, o robô e o autor de uma agenda ou de um webhook, mudar o que foi removido e voltar a versão da chave; ocorrências, entregas, lotes e linhas só aceitam inclusões, e a aplicação nunca apaga nada.
- **Resíduos conhecidos.** O limite por webhook e os baldes da `WebhookGate` ficam na memória de cada processo (com várias réplicas, é a soma). A primeira entrega com um identificador de webhook que não existe ainda custa uma consulta ao banco antes do 401 (as seguintes, por um minuto, não), dentro dos baldes; um ataque com muitos endereços de origem esgota o balde do processo e faz as entregas legítimas receberem 429 enquanto durar (o banco e as outras rotas ficam protegidos). Um xlsx cujos textos compartilhados chegam perto dos 64 MiB ainda custa cerca de meio gigabyte e alguns segundos para ler. Trocar `RAPA_CHAVE_WEBHOOKS` invalida as chaves de todos os webhooks (cada um precisa trocar a chave). Uma agenda continua rodando mesmo que a pessoa que a criou perca o papel: ela é da área, e quem opera a área a desliga.

## Regras do conserto (Consertar)

As regras completas estão nas docstrings de `rapa.core.snapshot`, `rapa.runner.snapshot` (e no cabeçalho de `rapa/runner/snapshot.js`), `rapa.repair.candidates`, `rapa.llm.repair`, `rapa.control.services.repairs`, `rapa.control.api.repairs` e da migração `v0005_conserto`. Em resumo:

- **O retrato.** Quando um passo com alvo falha com `elemento_nao_encontrado`, `elemento_ambiguo` ou `localizador_alternativo_em_gravacao`, o executor tira, uma vez por execução (no passo mais interno), um retrato só de leitura dos elementos visíveis que podem ser o alvo de um passo daquele tipo, em cada quadro (até 8, com 4 níveis de iframe): papel, nome acessível, rótulo, placeholder, texto, `data-testid`, id, `name`, o iframe, a linha de tabela em volta (o texto, as células e a chave) e quantos elementos do documento e dos shadow roots abertos casam com cada um, como o gravador mede. O script só lê o DOM, depois da falha: nenhum evento, foco ou rolagem, e nunca o valor de um campo (nem o `value` de um `<input>`, nem a opção escolhida, nem o texto de um elemento editável — `contenteditable` — ou de um `<textarea>`, também quando estão numa célula de tabela; o que fica dentro de um editor não entra). Os valores das credenciais digitadas e das entradas da execução (também os números, como o executor os digita) saem de todo texto (viram `REMOVIDO`, sem distinguir maiúsculas, e nunca viram localizador) nas formas em que o retrato os guarda: como vieram, com os brancos juntados, codificados num endereço e pelo começo de um valor longo; a limpeza vem antes do corte de cada texto, então um valor no limite nunca fica pela metade. Os endereços perdem a consulta, o fragmento e o usuário, e o `src` de um iframe com usuário e senha ou que não é http(s) (`data:`, `blob:`) fica de fora, e cada campo leva as marcas de sigilo do gravador (`rapa.recorder.sensitivity`). Até 150 elementos e 1 MiB; o que passa disso fica de fora (`truncated`). O retrato vai no resultado (`RunResult.failure_snapshot`), é conferido de novo pelo despachante (um retrato inválido fica de fora, e o resultado é gravado do mesmo jeito) e fica em `run_snapshots`, só em execuções que não deram certo. É melhor esforço: sem retrato (prazo de 4 s, que vale também para a limpeza dos valores, página fechada), a execução termina igual; um retrato que o banco recusa (um caractere nulo, o tamanho do texto do jsonb) fica de fora num ponto de salvamento, e o resultado da execução é gravado do mesmo jeito.
- **Os candidatos.** Saem só do retrato (`enumerate_candidates`): nada é executado de novo, muito menos um passo que grava. O tipo do passo manda (um clique só aceita botões, links, itens de menu, abas, opções e caixas; digitar, só campos de texto; escolher, só `<select>`; marcar, só caixas e opções; anexar, só `<input type=file>`; ler uma tabela, só tabelas), passos que agem pedem elementos habilitados, e a senha, o usuário e o código do cofre só vão para o campo que o gravador reconheceria como tal num login (`credential_kind`); um texto digitado nunca vai para a senha de um login. O alvo de cada candidato é montado por `build_target` do compilador, com as contagens do retrato: só localizadores únicos no documento, nunca só o caminho CSS, nunca um que só é único dentro de uma linha se o passo não escolhia linha. Num passo dentro de uma linha (`within_has_text`), a linha continua a mesma e só entram papel e nome ou texto únicos na linha, sem a chave dela. Um alvo que depende de um valor da execução (um localizador com `{{ item.numero }}` ou `{{ inputs.uf }}`) não é consertado (409): trocar por um texto do retrato faria o passo agir sempre no mesmo item. Um passo que não é irreversível nunca vai para um botão, link ou item de menu com verbo irreversível (emitir, enviar, concluir, excluir...), pela mesma regra do compilador: a proteção dos passos irreversíveis depende do efeito declarado. Um iframe achado só pelo endereço é procurado pelo caminho sem a consulta (`iframe[src="P"]`, `[src^="P?"]`, `[src^="P#"]`); um endereço com `REMOVIDO` não identifica o quadro e o candidato fica de fora. A nota (0 a 100) soma o mesmo papel de antes, as palavras em comum com a intenção e os localizadores antigos (com sinônimos comuns de portais), um texto igual, o mesmo iframe, um localizador único e o elemento habilitado; os candidatos vêm da maior nota para a menor (`RAPA_CONSERTO_CANDIDATOS`, 8 por padrão).
- **O modelo propõe, o código decide, a pessoa escolhe.** O modelo recebe o passo, os localizadores antigos, o endereço e o título da página e os candidatos (sem valores nem segredos, com o texto da página neutralizado e entre delimitadores) e responde `{"candidate_id": "c2" ou null, "reason": "..."}`, validado por um esquema com os números desta lista (`enum`), com o raciocínio desligado; um número fora da lista é perguntado de novo e, se continuar, recusado. A pergunta ao modelo tem 8 s (`SUGGESTION_TIMEOUT_S`), menos que o prazo da tela e do REST. Com o hub fora do ar ou lento, sem hub, sem a matriz da sonda ou com a resposta recusada, a tela mostra os candidatos do mesmo jeito, com o aviso, e a pessoa escolhe sozinha ("se o hub cair, só a criação de robôs para"). Nada vem escolhido na tela. A sugestão fica na memória do processo por uma hora (por execução e retrato); cada pergunta ao modelo entra na auditoria (`conserto.sugestao_pedida`).
- **Sempre um rascunho novo, publicado por outra pessoa.** O conserto nunca muda uma versão publicada: cria a próxima versão, em rascunho, só com o alvo daquele passo trocado (o efeito, o valor e os outros passos ficam iguais), pelo mesmo caminho de toda versão (`insert_version`: papel de criação, portão de política e auditoria), na mesma transação que registra o conserto (`repair_proposals`, `conserto.pedido`). A versão é de quem pediu, que por isso nunca a publica (a regra de sempre, também no banco); o modelo nunca é autor nem aprovador. Ver os candidatos pede o papel de criação ou de aprovação na área; pedir o conserto, o de criação; para outra área ou outra empresa, a execução não existe (404).
- **Quando não há conserto.** Só uma execução que falhou (nunca uma indeterminada: depois de um passo irreversível, uma pessoa confere o sistema de destino antes), num daqueles códigos, com retrato, e da versão mais nova do robô (consertar uma versão antiga desfaria o que veio depois); um conserto por execução. Robôs com certificado A1 não têm conserto assistido (403: nem candidatos, nem modelo, nem rascunho): "o conserto nunca é automático nessas sessões", e o conserto deles é uma gravação nova, acompanhada pelo custodiante.
- **Os dados.** `run_snapshots` (o despachante só inclui; a aplicação só lê) e `repair_proposals` (a aplicação lê e inclui) têm a empresa liderando as chaves, isolamento por linha (ENABLE e FORCE) e só aceitam inclusões.
- **Resíduos conhecidos.** O script do retrato roda no mundo da página: uma página que troca os protótipos do DOM pode mentir sobre os elementos (o pior caso é um candidato ruim, que a pessoa vê, outra aprova e o executor ainda confere na hora). Uma execução com listas de entrada muito grandes pode ficar sem retrato (a limpeza dos valores passa do prazo; falha fechada). Numa página com mais de 6000 elementos, as contagens ficam de fora e os localizadores entram sem conferência de unicidade (o executor confere na execução). A sugestão guardada fica na memória de cada processo (com várias réplicas, o modelo pode ser perguntado de novo). Um passo dentro de uma linha ambígua continua ambíguo depois do conserto (o conserto troca os localizadores, não a linha). O título do passo não muda com o conserto, só a intenção do alvo. A validação antes de publicar continua sendo a de sempre (marcar como validada).

## Regras do certificado A1

As regras completas estão nas docstrings de `rapa.control.services.credentials`, `rapa.control.services.a1`, `rapa.control.services.robots` (publicar), `rapa.control.api.credentials` e da migração `v0006_regras_a1`. Em resumo:

- **Só a referência.** O valor de uma credencial nunca passa pelo RaPA: `PgCredentials.register` grava o caminho no cofre (`vault_path`) e os metadados (nome, tipo, origem, custodiante e, no certificado A1, a validade `not_after` e a impressão SHA-256). O caminho no cofre só aparece para quem administra a área e para o custodiante, nunca na auditoria, no log ou no despachante. Registrar é de quem administra a área (`area_admin`, ou `company_admin`); o certificado A1 exige o custodiante (um usuário ativo da empresa, com o papel `credential_custodian` na área ou na empresa inteira, que não é quem registra) e a validade no futuro. A origem passa pela mesma normalização do manifesto (`normalize_origin`). `PgProvisioning.register_credential` continua para a automação de cadastro e os testes.
- **Custodiante.** Só ele renova a validade (o certificado novo no cofre) e autoriza um robô a usar o certificado (`a1_authorizations`, com a impressão do momento; uma ativa por robô e credencial): o robô precisa declarar o certificado na versão mais nova, com a mesma origem registrada, o certificado não pode estar revogado nem vencido, e o custodiante nunca autoriza um robô cuja versão mais nova (ou a publicada) ele criou. Renovar com outra impressão revoga as autorizações da anterior; sem a impressão, a renovação só vale para um certificado registrado sem ela (as autorizações continuam) e, com uma registrada, é recusada (422), em vez de apagar a impressão sem saber se o certificado mudou. Revogar a credencial (custodiante ou quem administra a área) revoga junto as autorizações dela; revogar uma autorização também é do custodiante ou de quem administra a área.
- **Dois aprovadores.** Publicar é aprovar (`version_approvals`): um robô cujo manifesto declara um `pfx_a1` precisa de duas aprovações de pessoas diferentes; os outros, de uma (o comportamento de antes, agora com a linha da aprovação). Cada aprovador tem o papel de aprovação na área, não criou a versão, não aprovou antes (409: "você já aprovou esta versão; falta a aprovação de outra pessoa") e, no A1, não é o custodiante de nenhum certificado do robô (403, separação de funções). Como a autorização do custodiante é do robô, e não da versão, uma versão criada por um desses custodiantes também não recebe aprovações (403): senão ela rodaria com a autorização dele. Antes de contar a aprovação, cada certificado do manifesto precisa estar registrado na área do robô com o mesmo nome, o tipo `pfx_a1` e a mesma origem, não revogado, não vencido e com a autorização ativa do custodiante para este robô na impressão atual; senão, 422 (`certificado_a1_bloqueado`) com a lista do que falta. Enquanto faltar aprovação, a versão continua validada e a resposta mostra `approvals` e `approvals_required` (a tela mostra "1 de 2 aprovações"); a última publica (`approved_by` é ela). No banco, o gatilho `rapa_robot_versions_approvals` recusa virar `published` sem as aprovações que o manifesto pede e recusa incluir uma versão que não nasce rascunho sem aprovador (incluir a versão já publicada pularia as aprovações); `rapa_version_approvals_check` recusa a aprovação de quem criou, a de uma versão que não está validada e, no A1, a do custodiante e a de uma versão que o custodiante criou. A tela do robô espelha tudo isso (`publish_block_reason`, com o que falta no certificado): o botão "Aprovar"/"Publicar" só aparece quando o servidor aceitaria. As versões publicadas antes da migração ganharam a aprovação de quem as publicou.
- **Na hora de rodar.** `enqueue_run` e `enqueue_many` (REST, MCP, interface, validação, agenda, webhook e lote) conferem as mesmas condições e recusam com `CertificateBlocked` (422, `certificado_a1_bloqueado`, com a lista); a agenda registra a ocorrência como ignorada (`certificado_bloqueado`). O despachante confere de novo logo antes de lançar o executor, com o papel dele (que só lê as colunas de que precisa de `credentials` e de `a1_authorizations`, nunca `vault_path`): se não valer mais, ou se a conferência falhar, nada é lançado e a execução termina `failed` com o código `certificado_a1_bloqueado`.
- **Vencimento.** Uma etapa do laço do despachante (`CredentialAlerts`, a cada 6 horas) acha os certificados A1 não revogados que vencem em até `RAPA_A1_AVISO_DIAS` dias (30 por padrão) ou já venceram e registra no máximo um aviso por credencial, dia (no fuso de Brasília) e tipo (`credential_alerts`, `vencendo` ou `vencida`), em lotes de 500, cada um numa transação curta e só com os que ainda não têm o aviso do dia (os vencidos que ninguém revoga não tomam o lugar dos outros), com a auditoria `credencial.a1_vencendo` ou `credencial.a1_vencida` e um WARNING no log só com o nome da credencial, a empresa e a data. A tela mostra o aviso no topo para custodiantes e administradores e a lista na tela Credenciais; o REST tem `GET /v1/credenciais/vencimentos`. Na tela Credenciais, quem administra a empresa inteira registra também numa área que a tela não conhece (sem robôs nem credenciais), pelo identificador. Um A1 registrado antes da migração, sem validade, continua no banco (a restrição é `NOT VALID`) e conta como vencido.
- **Conserto.** A interface não mostra "Consertar este passo" para um robô com A1 (`can_repair` olha o manifesto da versão; sem o manifesto, também não mostra) e o serviço continua recusando (403).
- **Os dados.** `a1_authorizations`, `version_approvals` e `credential_alerts` têm a empresa liderando as chaves e isolamento por linha (ENABLE e FORCE). Aprovações e avisos só aceitam inclusões; a autorização só muda para ser revogada, uma vez; da credencial só mudam a validade, a impressão e a revogação (uma vez), e a aplicação não apaga credenciais. A aplicação só lê os avisos; o despachante só os inclui. As permissões das revisões anteriores não mudam (a 0001 continua concedendo o que concedia); `a1_revokes_sql` tira o `UPDATE` e o `DELETE` amplos de `credentials` só quando as tabelas da 0006 existem, e voltar para a 0005 devolve exatamente as permissões de uma 0005 nova (o despachante deixa de ler `credentials`).
- **Resíduos conhecidos.** A impressão do certificado é a que quem registra e o custodiante informam: o RaPA não lê o PFX (o cofre e o lançador ainda não entregam o arquivo; a parte E liga o OpenBao), então a conferência da impressão vale tanto quanto o registro. A renovação no cofre e o registro da validade são dois passos: entre um e outro, as execuções seguem a validade registrada. O custodiante é uma pessoa: se ele perde o papel, ninguém renova nem autoriza até outro ser registrado (o administrador da área ainda revoga). A separação de funções compara sujeitos: uma mesma pessoa com dois logins diferentes passa por duas. Um aviso de vencimento a mais pode sair no mesmo dia se o certificado vence entre duas voltas (um `vencendo` e um `vencida`). Apagar a empresa (parte D2) precisa liberar também as travas de `a1_authorizations`, `version_approvals` e `credential_alerts`.

## Regras da operação por empresa

As regras completas estão nas docstrings de `rapa.control.services._common` (`ensure_company_active`), `rapa.control.services.company`, `rapa.control.services.lifecycle`, `rapa.control.services.principals`, `rapa.control.auth`, `rapa.control.api.company` e da migração `v0007_operacao_empresas`; o roteiro da plataforma está em [OPERACAO.md](OPERACAO.md). Em resumo:

- **Congelada: lê tudo, nada novo acontece.** `companies.status` é `active` ou `frozen` (com o motivo e o momento). Uma função só, `ensure_company_active`, recusa com `CompanyFrozen` (um `Conflict`; a API responde 423, `empresa_congelada`) no começo de toda escrita: `enqueue_run` e `enqueue_many` (REST, MCP, interface, agenda, webhook e lote), criar, validar e publicar versões, criar e mudar agendas, webhooks e lotes, abrir sessão de gravação e pedir conserto. Ela toma, compartilhada e primeiro na transação, a trava consultiva da situação da empresa (classe 7130); congelar e apagar tomam a mesma trava, exclusiva, também primeiro: quem congela espera as escritas em andamento, e as que chegam depois já veem a empresa congelada (a ordem igual das travas evita o impasse; `lock_company_starts` também a toma antes da trava de inícios). No banco, `rapa_company_active_guard` (`BEFORE INSERT`, a mesma trava compartilhada antes de ler a situação) recusa a linha nova de empresa congelada em execuções, robôs, versões, agendas, webhooks, lotes, sessões de gravação e consertos, mesmo de um caminho que esqueça `ensure_company_active`. Ao congelar, as execuções na fila viram `cancelled` com o código `empresa_congelada` (auditadas); as que rodam terminam normalmente. O despachante não pega nada de empresa congelada (nem conta a fila dela na admissão), e o recolhedor cancela, em vez de devolver à fila, a execução dela que perdeu o executor sem ter gravado. As agendas registram a ocorrência como pulada (`empresa_congelada`); o webhook, depois de conferida a assinatura, responde 423 sem criar nada (sem a assinatura certa, continua 401). Tirar papéis, desativar pessoas e remover agendas e webhooks continuam valendo (só diminuem o que acontece).
- **Só o dono das tabelas muda a situação.** A aplicação continua sem `UPDATE` em `companies`; congelar, descongelar, exportar e apagar são da linha de comando, com a URL do dono (`--url-dono` ou `RAPA_OWNER_DATABASE_URL`), e conferem que a transação é do dono antes de tudo. O despachante só lê `companies.id` e `companies.status`.
- **A empresa do token.** O `TokenVerifier` acha a empresa pelo mapa estático (`RAPA_ORGANIZATION_ALIASES`), pelo vínculo no banco (`companies.idp_organization`, o id do objeto do Keycloak ou o apelido) e, como antes, pelo id do objeto quando ele é o próprio id da empresa. O formato diz qual dos dois o vínculo guarda: no formato de UUID é sempre o id (na forma canônica, a do token); o apelido nunca tem esse formato. O id do token só é procurado como id e o apelido só como apelido, então uma organização cujo apelido é o id de outra não chega à empresa dela. O banco é lido por `rapa_company_for_organization(text)`, `SECURITY DEFINER` (dona: o dono das tabelas, `search_path` fixo, `EXECUTE` só para a aplicação), que liga a marca `rapa.organization_lookup` só durante a consulta: a política `organization_lookup` de `companies` vale só para o dono, então a aplicação não usa a marca para ler outras empresas. Na memória, um cache de 60 s (`CachedOrganizationDirectory`, inclusive para "não ligada"). Se o mapa e o banco (ou o id e o apelido) apontam empresas diferentes, recusa; com o banco fora do ar, 503.
- **Primeiro login.** Com uma organização ligada explicitamente (mapa ou banco) e um sujeito que ainda não existe, o `Authenticator` cria o usuário sem papel (`UserProvisioner`, nome do claim `name` ou `preferred_username`, cortado em 200), com auditoria `usuario.criado_no_login`; a interface mostra só "Peça a um administrador da empresa para dar um papel". Desativado continua sem entrar; empresa congelada não ganha usuário novo; o `sub` é único na plataforma, então o de outra empresa é recusado; o id do objeto usado direto como empresa (sem vínculo) não cria ninguém.
- **A empresa administra a si mesma** (`PgCompanyAdmin`, `/v1/empresa`, tela Empresa). Quem administra a empresa lista usuários e papéis, dá e tira papéis (por área ou na empresa inteira), desativa e reativa usuários e cria e renomeia áreas; quem administra uma área só dá e tira os papéis dela (nunca `company_admin`, nunca na empresa inteira) e vê os papéis das áreas dele e os da empresa inteira. `PUT .../papeis` troca a lista inteira no escopo de quem chama; o resto fica. `platform_admin` nunca é dado nem tirado por aqui. Ninguém tira o último `company_admin` ativo (conferido no serviço, sob a trava das mudanças de papéis da empresa, e no banco pelo gatilho adiado `rapa_company_admin_guard`, em `memberships` e `users`, que toma a mesma trava no fim da transação) nem desativa a si mesmo. Tudo auditado.
- **Consumo** (`/v1/empresa/consumo?mes=AAAA-MM`, `empresa consumo`, cartão na tela Empresa): por área e por origem, execuções por situação, minutos de navegador (`finished_at - started_at` de cada execução que começou e terminou), minutos das sessões de gravação (`stopped_at - started_at`), lotes e linhas, pelo mês do fuso `America/Sao_Paulo` em que cada coisa foi pedida. Vê quem administra a empresa e quem tem `auditor` (na empresa: todas as áreas; numa área: só ela). Lê pelos índices `runs_company_created`, `batches_company_created` e o novo `recording_sessions_company_created`.
- **Exportar e apagar.** A exportação lê toda tabela com `company_id` pelo catálogo (tabelas novas entram sozinhas), das mães para as filhas e pela chave primária, numa leitura `REPEATABLE READ`; colunas `bytea` (o sal dos webhooks) e geradas ficam de fora do valor. Os arquivos da empresa são percorridos por descritores (`os.fwalk`, sem seguir links) e cada um é aberto uma vez, com `O_NOFOLLOW`, e copiado para a pasta de trabalho enquanto o SHA-256 é calculado; é a cópia que entra no `.tar.gz`, então um arquivo trocado por um link no meio do caminho não é seguido e o manifesto sempre confere. Apagar exige a empresa congelada, o nome exato, nenhuma execução rodando e nenhuma sessão aberta; grava `empresa.apagada` em `platform_events` (sem empresa, só o dono lê e escreve, só inclusões), apaga das filhas para as mães (conferindo as contagens) e por fim a empresa, numa transação que marca `rapa.purge_company`. As travas de "só inclusões" e as que proíbem apagar (versões, sessões, agendas, webhooks) aceitam a exclusão de uma linha só quando a transação é do dono da tabela e a marca é a empresa da linha (`rapa_purge_allowed`). Depois saem as pastas da empresa (um link no lugar da pasta some sozinho, nunca o destino) e o `KeyDestroyer` é chamado.
- **O cadastro também é auditado.** `PgProvisioning` (os comandos antigos `empresa NOME`, `area` e `usuario`, a automação de cadastro e os testes) audita cada mudança na mesma transação, com o ator `plataforma:<quem pediu>` (`--por`): `empresa.criada`, `empresa.cota_alterada`, `area.criada`, `usuario.criado`, `usuario.papeis_alterados` (inclusive `platform_admin`) e `credencial.registrada`.
- **Resíduos conhecidos.** Os comandos antigos continuam sem o vínculo com a organização, e `usuario` cria a pessoa e cada papel em transações separadas (como antes). Um vínculo novo ou trocado demora até 60 s em cada processo (o cache). O consumo conta só a última tentativa de uma execução devolvida à fila (o início é refeito); a execução que ainda roda e a sessão ainda aberta entram na contagem, mas os minutos delas só quando terminam. Os gatilhos do banco da empresa congelada só olham as linhas novas (mudar o que já existe, como uma agenda, fica no serviço, porque o despachante também atualiza essas linhas); o do último administrador confere numa transação `READ COMMITTED` (a da aplicação). O motivo do congelamento é texto livre da plataforma, mostrado a quem administra ou audita. Sem o cofre, o `KeyDestroyer` local só registra (a parte E liga o OpenBao).

## Regras das evidências (telas, vídeo da falha e retenção)

As regras completas estão nas docstrings de `rapa.core.artifacts`, `rapa.control.artifacts`, `rapa.control.services.artifacts`, `rapa.control.services.retention`, `rapa.control.api.artifacts`, `rapa.runner.video`, `rapa.ui.evidence` e da migração `v0008_retencao`. Em resumo:

- **Onde ficam.** O executor guarda as telas, os arquivos baixados e o vídeo da falha na pasta da tentativa (`<RAPA_PASTA_ARTEFATOS>/<empresa>/<execução>/<tentativa>`). No fim da execução, o despachante registra cada um pelo `ArtifactStore` antes de gravar o resultado: o store local só aceita um arquivo comum que está na pasta da tentativa, com o nome dele (nunca outro caminho que o resultado do executor aponte); o que ele recusa fica de fora, e o resultado é gravado do mesmo jeito. Abaixo da raiz, o store nunca segue um atalho: a pasta da empresa, a da execução, a da tentativa e o arquivo são abertos um de cada vez, sem seguir atalho, para registrar, ler e apagar; uma pasta trocada por um atalho para a de outra execução ou empresa, mesmo dentro da raiz, é recusada (um FIFO no lugar do arquivo também, sem travar). `runs.artifacts` guarda o nome, o tipo, o tamanho, o SHA-256, a tentativa e a data, nunca o caminho do disco. O nome é o que o executor saneia (`[A-Za-z0-9._-]`, começa com letra ou número, pontos seguidos viram um só), a mesma regra que o plano de controle confere. A saída de um passo de download é o nome do artefato (o identificador que a API usa). O store de objetos com cifra por execução (parte E) entra pelo mesmo protocolo.
- **Quem vê.** Quem vê a execução vê os artefatos (`GET /v1/execucoes/{id}/artefatos` e `.../artefatos/{nome}`, e a tela da execução). Para outra área ou empresa, a execução não existe (404); um nome com barra, com `..`, fora da regra (`[A-Za-z0-9._-]`) ou que não está na lista da execução também não. O arquivo sai com o tipo dele; só a tela PNG e o vídeo WebM abrem na página (`inline`), o resto vai como anexo; sempre `nosniff`, `Cache-Control: private, no-store` e `Content-Security-Policy: default-src 'none'; sandbox`. A interface serve os arquivos pela própria rota (`/execucoes/{id}/artefatos/{nome}`), com a sessão do cookie, pelo backend direto ou pelo REST.
- **Vídeo só em falha.** Com `RAPA_VIDEO_EM_FALHAS` (ligado por padrão), o contexto do navegador filma a página do robô (1280x800). Se a execução dá certo (ou é cancelada), o vídeo é apagado sem virar artefato; se falha ou fica indeterminada, vira o artefato `video`, também quando o lançador interrompe o worker no fim do prazo e a execução fica indeterminada. A gravação é só observação: se o vídeo não abre (sem o `ffmpeg` do Playwright, por exemplo), o robô roda num contexto igual ao de sempre, e o servidor avisa no log ao subir; um erro ao fechar ou guardar o vídeo só o deixa de fora; fechar o vídeo tem limite próprio de 10 s, que o lançador soma à folga depois do prazo. O vídeo mostra a tela como ela é: por isso um robô que digita o usuário ou o código TOTP do cofre (que vão para campos comuns) nem é filmado, e o campo de cada senha é conferido antes e depois de digitar, com o tipo dele vigiado no meio; se ele não for `<input type=password>` antes ou depois (um "mostrar senha" ligado que a página desliga ao digitar), se o tipo mudar no meio, ou se a conferência falhar, o vídeo não é guardado. No CI, o `ffmpeg` do Debian é instalado e os testes que filmam não podem ser pulados (`RAPA_TEST_VIDEO_OBRIGATORIO=1`).
- **Retenção.** O despachante roda a etapa `retention` uma vez por hora (a cada minuto enquanto fica para trás), em lotes pequenos que se revezam, cada um numa transação curta, com tempo limitado por volta. As telas e o vídeo (e o que sobrou de outra tentativa) de execuções que deram certo ou foram canceladas saem depois de `RAPA_RETENCAO_SUCESSO_DIAS` (7), e a execução ganha a marca `captures_expired_at`; os arquivos baixados por elas ficam. As evidências (todos os artefatos de falhas e indeterminadas, e os arquivos baixados das que deram certo) e os retratos das falhas saem depois de `RAPA_RETENCAO_FALHAS_DIAS` (90), com a marca `artifacts_expired_at`; as chaves de idempotência vencidas são apagadas; as partições de eventos que terminaram há mais de `RAPA_RETENCAO_EVENTOS_DIAS` (400) são removidas. Todos os prazos têm no mínimo 1 dia e estão **a validar com o jurídico**. Os arquivos de uma execução são apagados antes de a marca ser gravada, na mesma transação; a lista de artefatos fica, e a API mostra `expirado` e responde 410 em cada arquivo que a marca cobre (com `captures_expired_at`, só as telas e o vídeo). Cada execução expirada (as capturas ou tudo) e cada retrato apagado entram na auditoria da empresa.
- **Os dados.** O despachante não tem `DELETE` em nenhuma tabela: os retratos, as chaves e as partições saem por funções `SECURITY DEFINER` (donas: o dono das tabelas; `EXECUTE` só para o despachante; `search_path` fixo) que recebem só a idade e o tamanho do lote. Elas enxergam todas as empresas por políticas `retention_sweep_*`, só para ler e apagar, restritas ao papel dono e à marca `rapa.retention`, que a própria função põe logo antes de apagar e tira logo depois; a trava de só inclusões de `run_snapshots` aceita só essa exclusão, de um retrato com mais de um dia. Na execução, as duas marcas de expirado são as únicas colunas que a retenção muda: marcar não muda mais nada, uma marca nunca é desfeita e a lista de artefatos não muda depois da primeira (trava `runs_artifacts_guard`). São duas porque os arquivos baixados de uma execução que deu certo ficam além das telas: sem a segunda marca, a retenção teria de reler, a cada hora, todas as execuções que deram certo para saber quais já perderam as telas. A migração tira o caminho do disco das execuções que já existiam.
- **Resíduos conhecidos.** O vídeo não consegue mascarar campos como as telas: as entradas da execução digitadas em campos comuns aparecem nele (como nas telas, e o acesso é o mesmo), e uma página que mostra a senha em outro lugar enquanto ela é digitada (um medidor de força que repete o texto), que troca o campo de senha por outro elemento (um campo comum novo no lugar dele), que muda o tipo depois da conferência final, ou que mente sobre o tipo do campo trocando os protótipos do DOM (a conferência e a vigia rodam no mundo da página), mostra a senha. Só a página do robô é filmada; um popup não. Sem o `ffmpeg` do Playwright no executor (`playwright install ffmpeg`), nada é filmado (o servidor avisa no log ao subir, quando o executor roda na mesma máquina); a página de teste que confere o vídeo soma uma fração de segundo ao começo de cada execução filmada. A própria raiz dos artefatos (`RAPA_PASTA_ARTEFATOS`) pode ser um atalho: é a configuração do servidor. Um arquivo de um tipo que não é download conta como captura e sai no prazo curto (só o arquivo baixado é evidência). Se a gravação da marca falhar depois de os arquivos serem apagados, a API responde 404 ("não está mais guardado") até a próxima volta marcar a execução. Remover uma partição de eventos pede uma trava exclusiva em `run_events` por um instante (com o limite de espera da manutenção; se não conseguir, tenta na volta seguinte). Na integração com a migração 0007, a trava própria de `run_snapshots` (`rapa_run_snapshots_append_only`) precisa aceitar também a marca `rapa.purge_company`.
